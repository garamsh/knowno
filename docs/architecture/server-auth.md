# Server sign-in and account deletion

The server's Auth settings and email sign-in, App Review's sign-in function, and deleting an account.

## Current decisions

### Auth settings

- **What reaches production.** The Supabase GitHub integration deploys a merge's migrations, the functions and the Storage buckets `config.toml` declares, and "All other configurations, including API, Auth, and seed files, are ignored by default"; on a persistent branch such as production its configure step runs only when a `[remotes]` block names the project's ID, and then updates every differing value of the `[auth]` section, among others. `config.toml` has no `[remotes]` block, so its `[auth]` section configures the local stack alone and a merge changes no production Auth setting; the owner sets them in the dashboard or through the Management API ([ADR 0213](adr/0213-sign-in-by-email-with-a-six-digit-code-sent-in-korean-and-set-the-production-project-s-auth-by-hand-since-its-config-toml-section-is-not-applied.md); the integration's documentation, `supabase/supabase` at `156738417b699a499d1a1504b86fcc0459ec5a8c`, read 2026-11-09).
- **Email sign-in** ([ADR 0213](adr/0213-sign-in-by-email-with-a-six-digit-code-sent-in-korean-and-set-the-production-project-s-auth-by-hand-since-its-config-toml-section-is-not-applied.md), [`account.md`](account.md) §Sign-in and session): `[auth.email]` has `otp_length` 6, `otp_expiry` 600 seconds and `max_frequency` 60 seconds, sign-up enabled and email confirmation off locally. `supabase/templates/sign_in_code.html`, Korean, shows `{{ .Token }}` and its 10 minutes with no link, and is the content of both `[auth.email.template.magic_link]`, sent to an address with an account, and `[auth.email.template.confirmation]`, sent to a new address while email confirmation is on, as it is by default on a hosted project; the expiry and the template's "10분" change together.
- **Production** holds the same values, set by hand: custom SMTP (host, port, user, password, sender address and name) on a sender domain with SPF, DKIM and DMARC; the email OTP expiration 600 seconds; the two templates; 60 seconds between emails to one address; and the project's emails an hour, 30 while custom SMTP is new. Without custom SMTP the built-in sender reaches only the project's organization's members, 2 messages an hour, so no other user can sign in by email at all. The owner's steps are in the ADR's Decision.
- The local stack's Mailpit holds every email it sends, at `http://127.0.0.1:54324` by default; the code is in the subject and the body.

### Review sign-in

- **What it is** ([ADR 0226](adr/0226-sign-one-app-review-address-in-through-the-review-sign-in-function-with-a-fixed-code-kept-in-vault-and-hand-the-app-the-token-hash-of-an-email-sign-in.md)). One address, the App Review address, signs in with one fixed code, both Vault secrets the owner creates, `review_sign_in_email` and `review_sign_in_code`; every other address keeps the email code of §Auth settings, whose 10-minute life and resend limits are unchanged. Apple's Guideline 2.1(a) asks for a demo account for an app with a login.
- **The function.** `review-sign-in`, `verify_jwt = false`, takes `POST` `{"email", "code"}` and answers:
  - `200` `{"token_hash", "type": "email"}` for the address and the code; the app exchanges the hash with `verifyOTP(tokenHash:, type: OtpType.email)` for an ordinary session ([`account.md`](account.md) §Sign-in and session);
  - `401` `refused` for anything else well formed, one body and one log line whether the address or the code was wrong, the address is not the review address, or a secret is unset;
  - `429` `rate_limited` with `Retry-After: 600`; `400` `bad_request`; `405`; `502` `unavailable`; `503` `not_configured`.
- **The session.** After a match the function asks Auth's admin API for a magic link of the address (`POST /auth/v1/admin/generate_link`, `type` `magiclink`), which sends no email and creates the user on first use, an ordinary 무료 account, and answers its `hashed_token`. It holds no access or refresh token.
- **Checks.** Address and code are compared as SHA-256 digests byte by byte, both always, and a secret that is unset or under 12 characters refuses every attempt. Each attempt, any address, is recorded under the address's SHA-256 in `private.review_sign_in_attempts` before a secret is read; over 5 attempts of an address or 20 in all within 10 minutes is refused with no secret read, and a row is deleted after a day. `public.review_sign_in_begin(address_key)` does that and reads the secrets from `vault.decrypted_secrets`; only `service_role` executes it.
- Migration `20261110090000_review_sign_in.sql` adds the table and the two functions, changes no row and no existing object, so it is additive ([`server.md`](server.md) §Location and migrations, "Gate"). **Revert:** `select private.revert_review_sign_in();` and then `drop function private.revert_review_sign_in();`, run once by the PM against production, drop the function and the table; the Vault secrets stay.
- **Owner's steps** (the ADR's Decision): an address no real account uses and that receives mail; a random code of at least 12 digits, digits only, 16 recommended, for example `LC_ALL=C tr -dc 0-9 </dev/urandom | head -c 16` ([ADR 0228](adr/0228-choose-app-review-s-sign-in-by-the-code-s-digit-count-keep-the-code-field-to-digits-and-sign-in-on-a-code-that-arrives-whole.md), which narrows ADR 0226's example); both secrets created in Vault; the address as User name and the code as Password in App Store Connect's sign-in information. Without the secrets every attempt is refused.

### Account deletion

- The `delete-account` Edge Function first deletes every file in the caller's folder of the `media` bucket, and then of the `assistant-photos` bucket ([`server-assistant.md`](server-assistant.md) §Photo jobs), through the Storage API, a page of 1000 at a time, then, for an account with an Apple identity and a code in the request body, revokes its Sign in with Apple authorization, which never stops the deletion ([`server.md`](server.md) §Edge Function deploys, "Secrets", [ADR 0210](adr/0210-revoke-the-apple-authorization-when-an-account-is-deleted-by-exchanging-a-fresh-authorization-code-at-deletion-and-never-let-a-failed-revocation-stop-the-deletion.md)), then deletes the caller's user from `auth.users` through Supabase Auth's admin API, with the service-role key, which stays in the function ([`account.md`](account.md), [ADR 0026](adr/0026-delete-the-account-through-an-edge-function.md)). The deletion is hard, so the cascade runs.
- Every table in `public` deletes with the user: `decks`, `cards`, `reviews`, `card_states`, `extraction_usage`, `media`, `profiles` and `study_settings` by `user_id`, `deck_reports` and `deck_copies` by their user and by their deck, and `user_blocks` by either side. In `private`, `admins`, `user_plans`, `user_plans_before_versions` and `suspensions` delete with their user, `deck_removals` with its deck, `extraction_calls` with its usage row and `extraction_calls_before_versions` with its call, and a granter or editor column, `admins.granted_by`, `user_plans.granted_by`, `user_plans_before_versions.granted_by`, `plan_versions.created_by`, `plans_before_versions.updated_by`, `suspensions.suspended_by`, `deck_removals.removed_by`, `prompt_versions.created_by` or `prompt_labels.set_by`, is set null; `admin_audit` keeps the admin's rows with `admin_id` set null. Another user's copy of a deleted user's deck stays theirs.
- A new table holding a user id references `auth.users` with `on delete cascade`, except a column naming who granted or edited a row, which is set null so the row outlives that admin, and `private.admin_audit`, whose rows outlive the admin who wrote them ([ADR 0070](adr/0070-run-the-service-from-a-web-admin-area-whose-role-and-audit-log-live-in-the-database-and-whose-every-read-and-write-is-checked-there.md)).
- Merging the pull request that adds or changes the function deploys it ([`server.md`](server.md) §Edge Function deploys).

## Rationale

- [ADR 0226](adr/0226-sign-one-app-review-address-in-through-the-review-sign-in-function-with-a-fixed-code-kept-in-vault-and-hand-the-app-the-token-hash-of-an-email-sign-in.md) records why the App Review address signs in through a function with a fixed code from Vault and hands the app a token hash, the contract the app calls, the limits, and the alternatives passed over: Supabase's phone test numbers, a demo mode, a password and Sign in with Apple alone.
- [ADR 0026](adr/0026-delete-the-account-through-an-edge-function.md) records why an account is deleted through the admin API, so that the cascade removes its rows.
