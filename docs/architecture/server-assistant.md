# Server assistant

The server's side of the assistant: its prompts, configurations, daily token budget and message record, the card-form skills, the card markup as the one format, and the photo jobs with their bucket and queue.

## Current decisions

### Assistant

- The assistant's server side ([`assistant.md`](assistant.md), [ADR 0190](adr/0190-serve-the-assistant-from-an-edge-function-that-streams-a-tool-loop-proposes-cards-in-groups-and-commits-what-the-user-checks-under-a-per-plan-daily-limit.md), [ADR 0195](adr/0195-meter-the-assistant-by-a-daily-token-budget-per-plan-charged-when-a-message-ends-shorten-a-resent-reply-and-save-a-draft-after-a-check-call.md)) is six tables in `private`, on which no client role holds a privilege:
  - `private.assistant_prompts` — the assistant's prompts, of `private.prompt_versions`' shape and append-only by its trigger function, `keep_prompt_version`; seeded with one, noted `말랑이 assistant prompt v1 (#713)`, and v2, noted `말랑이 assistant prompt v2, its working order and card forms (#751)`, appended by `20261105150000_card_form_skills.sql` (§Card-form skills);
  - `private.assistant_configurations` — each plan's assistant configurations, append-only by a trigger as ADR 0182's are: the plan, the provider and model, checked by `private.model_fits`, the prompt, `web_search`, `max_searches` from 1 to 10 and `reasoning_effort`, `none`, `low`, `medium` or `high`, which `private.assistant_effort_fits` checks against Anthropic's per-model thinking table for an Anthropic model: `none` refused where thinking is always on (Claude Fable, Mythos and Opus 5.5), any other effort where thinking is extended alone (Claude 4.5 and earlier Claude 4 models);
  - `private.assistant_configuration_labels` — each plan's `active` configuration, served to its users, and its one draft, `test`, served to admins;
  - `private.assistant_token_budgets` — each plan's `daily_tokens`, from 0 to 1,000,000,000 or null for none, who set it and when;
  - `private.assistant_limits` — each plan's `daily_messages`, the message limit the budgets superseded, read by nothing but the revert of `20261105090000_assistant_tokens.sql`;
  - `private.assistant_messages` — one row per message let through: the user, deleted with it, the plan, the configuration and the time, and once its turn ended its outcome (`ok`, `choice`, `depth_limit`, `time_limit`, `model_error`, `cut` or `cancelled`), model calls, input, output and reasoning tokens, web searches and latency, all null or all set; no text.
- **The charge.** A message is charged its input and output tokens once it is recorded; `private.assistant_tokens_today(user_id)` sums them over the user's messages since 00:00 in Asia/Seoul, a message not yet recorded charged nothing.
- `public.begin_assistant_message(user_id)`, executable only by `service_role`, resolves the plan through `private.entitlement_of` and the configuration serving the user, an admin's plan's draft while one is set and otherwise the active one, with its prompt and settings and whether its provider has a key. Under a transaction-level advisory lock on the hash of the user id seeded with 7, it reads the tokens charged today and whether another message of the user begun within 150 s is unrecorded (`busy`), and records one when the provider has a key, the tokens are under the budget or there is none, and it is not busy. It returns `token_budget`, `tokens_used` before this message, `busy`, `allowed` and the row's id; no row while the plan has no configuration or budget row.
- `public.finish_assistant_message(message_id, outcome, …)`, executable only by `service_role`, records a turn once, under the same lock of the message's user, which charges it: a message recorded already or never begun raises `P0002`.
- `public.assistant_allowance()`, executable by `authenticated`, answers the caller's `token_budget`, null for none, `tokens_used` today, as `begin_assistant_message` reads them, and `tokens_left`, null without a budget, naming no plan.
- `public.save_assistant_configuration(admin_id, plan, provider, model, prompt_version_id, web_search, max_searches, reasoning_effort)`, executable only by `service_role` and refusing an `admin_id` that is no admin, appends a configuration as the plan's one draft, each setting left null kept from the draft or else the active one, and records `save_assistant_configuration`; a prompt that does not exist, or a model that cannot run at the effort, answers null, recording nothing. The `assistant` function's `settings/configuration` calls it after its check call ([`assistant.md`](assistant.md) §Draft), having asked `public.assistant_effort_fits(provider, model, effort)`, executable only by `service_role`, which answers `private.assistant_effort_fits`.
- The admin functions, each checking the role and recording itself as [`server-admin.md`](server-admin.md) §Admin area states: `admin_assistant_prompts`, newest first with the labels of the configurations sending each; `admin_save_assistant_prompt(text, note)`; `admin_assistant_configurations`; `admin_activate_assistant_configuration(plan)`, under an advisory lock seeded with 8, refused while the draft's provider has no key; `admin_clear_assistant_test(plan)`; `admin_assistant_token_budgets`; and `admin_set_assistant_token_budget(plan, daily_tokens)`, recorded as `set_assistant_token_budget` with the budget before, which answers `unchanged`, `bad_plan` or `bad_budget` recording nothing.
- Migration `20261104150000_assistant.sql` is additive: it creates the tables, their indexes, triggers and functions, and seeds the prompt; each plan's active configuration on the provider and model of its active photo configuration, with web search off for Free and on for Pro, Max and 스페셜, 3 searches and no reasoning, or effort `low` on a model whose thinking is always on, through `private.seed_assistant_configurations()`, which stays; and the limits, Free 10, Pro 100, Max 300 and 스페셜 none. It inserts, changes and deletes no row of an existing table.
- **Revert.** `select private.revert_assistant();` and then `drop function private.revert_assistant();`, run once by the PM against production, drop every function and table the migration made, the message rows with them. After `20261105090000_assistant_tokens.sql`, its revert runs first.
- Migration `20261105090000_assistant_tokens.sql` changes no row of an existing table: it creates `private.assistant_token_budgets`, seeded with the budgets the owner approved on 2026-11-05, Free 200,000, Pro 2,000,000, Max 6,000,000 and 스페셜 none, `private.assistant_tokens_today` and `public.assistant_effort_fits`; it replaces `begin_assistant_message`, `finish_assistant_message` and `assistant_allowance`, and the limit's admin functions with the budget's. Since it changes what a message costs, it merges with the owner's approval ([`server.md`](server.md) §Edge Function deploys, "Gate").
- **Its revert.** `select private.revert_assistant_tokens();` and then `drop function private.revert_assistant_tokens();`, run once by the PM against production, put the five functions back as `20261104150000_assistant.sql` made them, reading the kept limits, and drop the budget table and its functions; the message rows stay.

### Card-form skills

- The card-form skills ([`assistant.md`](assistant.md) §Card forms, [ADR 0197](adr/0197-make-the-card-forms-versioned-skills-an-index-the-assistant-always-sees-and-a-guide-per-form-it-loads-shared-with-mcp-and-hold-each-proposal-group-to-one-form.md)) are two tables in `private`, on which no client role holds a privilege:
  - `private.card_form_skills` — every saved version: an identity `id`, the `form`, one of `text`, `senses`, `cloze`, `table`, `image` and `mixed`, a one-line `summary` of at most 300 characters, the guide's `text` of at most 20,000, a `note` of at most 200, `created_by`, set null when that account is deleted, and `created_at`; append-only by its trigger function, `keep_card_form_skill`, but for that author's removal;
  - `private.card_form_skill_labels` — each form's `active` version, served to everyone, and its `test` version, while set, served to admins; a label names a version of its own form.
- `public.card_form_skills()`, executable by `authenticated`, answers each form's version served to the caller, its id, summary and text: the test version for an admin while one is set, and otherwise the active one. The `assistant` and `mcp` functions call it with the user's token.
- The admin functions, each checking the role and recording itself as [`server-admin.md`](server-admin.md) §Admin area states, under an advisory lock seeded with 9 where they write: `admin_card_form_skills`, every version newest first with its text and labels; `admin_save_card_form_skill(form, summary, text, note)`, which saves a version, the summary and note trimmed, as the form's test version, replacing any, and answers its id (`save_card_form_skill` on a `card_form`); `admin_activate_card_form_skill(form)`, which makes the test version active and clears the test label, answering `activated`, or `no_test` recording nothing (`activate_card_form_skill`, with the version before); and `admin_clear_card_form_skill_test(form)`, true when it ended one (`clear_card_form_skill_test`). The admin pages that call them are #751's next pull request.
- Migration `20261105150000_card_form_skills.sql` creates the tables, their indexes, the trigger and the functions, and seeds each form's first version, `card_forms_seed.ts`'s texts, as active. It also appends to the assistant's tables, changing and deleting no row of them: prompt v2, and while 스페셜, the admins' plan, has no assistant draft, its active configuration with prompt v2 as its `test` label, so admins are served it; no other plan gets a draft, since 말랑이 opens on the first plan with one.
- **Revert.** `select private.revert_card_form_skills();` and then `drop function private.revert_card_form_skills();`, run once by the PM against production, end the draft that sends prompt v2 and drop the tables and functions the migration made; a plan whose active configuration sends prompt v2 keeps it. It runs before `revert_assistant_tokens()` and `revert_assistant()`, since it deletes from a table the assistant's revert drops. The `assistant` and `mcp` bundles go back with it, to those before the change: the bundles of the change read `card_form_skills` and without it answer every message 503 and every resource read `-32603`.

### Card markup

- The card markup is the only card text format the server accepts, writes and teaches ([ADR 0254](adr/0254-write-only-the-card-text-markup-and-anki-cloze-everywhere-convert-stored-cards-and-remove-the-switch.md), which supersedes [ADR 0216](adr/0216-write-the-card-text-markup-behind-a-database-switch-off-until-a-release-that-reads-it-is-on-testflight-and-serve-its-skills-only-while-it-is-on.md)): a `text` block is written at version 3, its front and back markup, and a `cloze` block at version 2, `{text}` in Anki's syntax. No switch decides it: `private.server_switches`, `card_markup_enabled`, `admin_card_markup` and `admin_set_card_markup` are gone, and no function of `supabase/functions/` reads one.
- The card tools of the assistant and MCP write nothing else ([`mcp.md`](mcp.md) §Tools): a cloze in the older form, `text` with `___` and `answers`, is refused with a sentence that gives the form to send. A stored block of any version is shown as stored by `list_cards`, `search_cards` and the study record.
- Migration `20261112120000_card_markup_only.sql` converts every stored `text` block below version 3 and `cloze` block below version 2 ([`server-migrations.md`](server-migrations.md) §Card markup migration), drops the switch and its two revert functions, and appends a version of `text`, `cloze` and `mixed`, `card_forms_seed.ts`'s `SEED`, that teaches the markup and no longer calls the older cloze form accepted, labelled `active` in place of the version served; the `markup` labels are removed and the label check, `card_form_skills()` and `admin_activate_card_form_skill` are as `20261105150000_card_form_skills.sql` made them. No older version is served; an admin's `test` label is left. The `assistant`, `mcp` and `extract-cards` bundles of the change deploy with it, and the bundles before it read `card_markup_enabled`.
- **Revert.** The cards' revert is in [`server-migrations.md`](server-migrations.md). The switch and the skills' labels have none, on purpose: the switch was off and never set, so there is no behaviour to put back, and versions are append-only, so an admin serves an earlier one through the `test` label and `admin_activate_card_form_skill`.
- A skill change reaches a caller within `SKILL_CACHE_MS`, 60 seconds.

### Photo jobs

- 말랑이's photo jobs ([`assistant.md`](assistant.md) §Photo jobs, [ADR 0198](adr/0198-read-the-chat-s-photos-in-a-background-job-on-supabase-queues-each-photo-a-step-of-the-assistant-s-model-charged-against-the-day-s-tokens.md)):
  - the private bucket `assistant-photos`, each photo `{owner}/{photo id}`, a uuid, of `image/jpeg`, `image/png` or `image/webp`, at most 6 MiB, photo import's limit; `supabase/config.toml` declares the same for the local stack. Policies on `storage.objects`: its owner uploads only into its own folder under a uuid, and reads and deletes its own; a restrictive policy refuses a suspended user's upload; none allows an update;
  - the pgmq extension, Supabase Queues, and its queue `assistant_photo_reads`, one message a photo, `{job_id, position}`;
  - three tables in `private`, on which no client role holds a privilege: `assistant_jobs`, a job with its user, deleted with them, plan, configuration, instructions of at most 4,000 characters, status `running`, `done` or `cancelled` and its times, one running a user; `assistant_job_photos`, each photo in order, at most 50, with its queue message while `queued`, its status, `read`, `failed`, `skipped` or `cancelled`, its reads begun, at most 3, and once read its reading, at most 50,000 characters, and whether it was cut; and `assistant_job_steps`, one read with the user, deleted with them, the job, set null when it is purged, the plan, the configuration and the time, and once recorded its outcome (`ok`, `cut`, `model_error`, `time_limit`, `unreadable` or `not_sent`), input, output and reasoning tokens and latency, all null or all set; no text.
- **The charge.** `private.assistant_tokens_today(user_id)` sums the recorded messages' and the recorded steps' input and output tokens since 00:00 in Asia/Seoul, so `begin_assistant_message`, `assistant_allowance` and the job functions count both.
- The functions, each executable only by `service_role`, `security definer` with an empty `search_path`, each taking the user's assistant lock, the hash of the user id seeded with 7, where it writes:
  - `public.start_assistant_job(user_id, job_id, photo_ids, instructions)` resolves the configuration as `begin_assistant_message` does and answers `started`, `unavailable`, `rate_limited`, `busy` (another job running), `bad_photos` (none, over 50, or one twice) or `missing_photos` (one not in the user's folder), with the plan, budget and tokens used; no row while the plan has no configuration or budget. A started job queues each photo;
  - `public.next_assistant_job_step()` reads the next message, hidden 150 s, and begins its step: a message whose photo is not queued is deleted; one of a user with three steps unrecorded within 150 s is hidden 5 s, as is one of a user whose lock another transaction holds, which the function only tries and never waits for, so it is in no cycle of waits ([ADR 0218](adr/0218-record-that-an-ended-photo-job-s-photos-were-deleted-and-let-the-worker-delete-the-rest-take-a-user-s-lock-without-waiting-and-retry-a-failed-read-after-30-and-120-seconds.md)); a photo whose job's plan has spent the day's budget is `skipped`, and one begun three times `failed`. It answers `step` with the step, the photo and the job's configuration and instructions, or `empty` with the messages still queued;
  - `public.finish_assistant_job_step(step_id, outcome, input_tokens, output_tokens, reasoning_tokens, latency_ms, reading, retry_after_seconds)` records a step once, a step recorded already or never begun raising `P0002`: a queued photo is read on `ok` or `cut`, failed on `unreadable` or its third read, and otherwise shown again in 30 s, or 120 s once read twice, or after `retry_after_seconds` (the last argument, null by default; at least 1 and at most 300) when the worker sends a 429 or 529's `Retry-After`; an outcome `not_sent`, a read that failed before its request was sent, is given back, taking one off the photo's `attempts` and showing it again in 30 s, while the photo has at most 3 steps of that outcome, this one included, and counts as any failed read after ([ADR 0221](adr/0221-wait-a-refused-photo-read-s-retry-after-up-to-300-seconds-and-give-back-a-read-that-failed-before-it-was-sent-three-times-a-photo.md)); a job with no queued photo is done. It answers the photo's and the job's status;
  - `public.cancel_assistant_job(user_id, job_id)` cancels the user's running job, its queued photos and their messages, answering `cancelled`, the status of a job that had ended, or null for no such job of the user's;
  - `public.assistant_job(user_id, job_id)` answers the user's job, its times, its last read begun and each photo with its reading; no row for another user's;
  - `public.assistant_jobs_to_clear()` lists, at most 20, the jobs that ended and whose `photos_cleared_at` is null, and `public.mark_assistant_job_cleared(user_id, job_id)` sets it on an ended job once the worker deleted its photos from the bucket, which SQL cannot do ([ADR 0218](adr/0218-record-that-an-ended-photo-job-s-photos-were-deleted-and-let-the-worker-delete-the-rest-take-a-user-s-lock-without-waiting-and-retry-a-failed-read-after-30-and-120-seconds.md)). A job ended in SQL, by the budget or a third read, is cleared by the next worker.
- **Charges and unread uploads** ([ADR 0219](adr/0219-charge-a-killed-photo-read-a-fixed-estimate-of-4784-tokens-close-its-step-in-the-sweep-and-delete-uploads-no-job-names-after-24-hours.md)). `private.assistant_photo_estimate_tokens()` is 4,784, what a failed read is charged; `private.sweep_assistant_jobs()` first records each step with no outcome begun over 150 s ago, 100 at most, as `time_limit` with it through `finish_assistant_job_step`, once, trying a user's lock and leaving that user to the next minute when it is held. `public.assistant_unread_photos()`, executable by `service_role`, lists at most 100 objects of `assistant-photos` older than 24 hours that no job photo row names, which the worker deletes; the cron job `sweep-assistant-unread-photos` runs `private.sweep_assistant_unread_photos()` daily at 18:45 GMT, requesting the worker when there are any. Migration `20261109210000_assistant_photo_charges.sql` changes no row and, since it changes what a read is charged, merges with the owner's approval ([`server.md`](server.md) §Edge Function deploys, "Gate"). **Revert:** `select private.revert_assistant_photo_charges();` and then `drop function private.revert_assistant_photo_charges();`, run once by the PM against production before `revert_assistant_photo_job_cleanup()`, unschedule the cron job, drop the three functions and put `sweep_assistant_jobs` back; steps already closed stay closed and charged. The `assistant` bundle goes back with it.
- **Purge.** A `pg_cron` job, `purge-assistant-jobs`, runs `private.purge_assistant_jobs()` daily at 18:30 GMT, deleting the jobs begun more than 7 days ago whose photos were recorded deleted, with their photos' rows; their steps stay.
- **Sweep** ([ADR 0203](adr/0203-resume-a-stalled-photo-job-from-the-server-with-a-pg-cron-sweep-that-requests-the-worker-through-pg-net-its-url-and-key-in-vault.md)). A `pg_cron` job, `sweep-assistant-jobs`, runs `private.sweep_assistant_jobs()` every minute. It requests the worker once, through `private.request_assistant_job_worker(function_url, service_role_key)` and pg_net's `net.http_post` (a POST of `{function_url}/jobs/work` with the key as `apikey` and bearer token), when a running job has a queued photo and has begun no read for 3 minutes, or, with none begun, started over 3 minutes ago: `STALE_MS` of the poll, or when a job ended over a minute ago with its photos still in the bucket. Neither function is executable by a client role. The URL is the Vault secret `project_url` followed by `/functions/v1/assistant` (§Photo jobs, "Project address"), and the service-role key the Vault secret `assistant_service_role_key`, read by name from `vault.decrypted_secrets`; with either missing the sweep does nothing and raises nothing, so local stacks, previews and CI need no secret. Migration `20261108120000_assistant_job_sweeper.sql` enables pg_net where it is not on, creates the two functions and the cron job, and changes no row and no existing object, so it is additive ([`server.md`](server.md) §Location and migrations, "Gate"); it read the secret `assistant_function_url`, which `20261111150000_project_url.sql` replaced. **Revert:** `select private.revert_assistant_job_sweeper();` and then `drop function private.revert_assistant_job_sweeper();`, run once by the PM against production, unschedule the cron job and drop the functions; pg_net and the secrets stay.
- **Project address** ([ADR 0245](adr/0245-reach-the-database-s-edge-function-callers-through-one-project-url-vault-secret.md)). The Vault secret `project_url`, `https://<project ref>.supabase.co`, is the one address of the project; each caller of an Edge Function appends the function's path, `/functions/v1/assistant`, `/functions/v1/publish-note` or `/functions/v1/triage-reports`, which lives in the migration that owns the caller: `sweep_assistant_jobs`, `sweep_assistant_unread_photos`, `sweep_deck_screening`, `sweep_report_triage` and `triage_severe_report`. A new function the database calls adds its path and no secret; with `project_url` missing every caller does nothing and raises nothing, and a per-function URL secret is not read. Migration `20261111150000_project_url.sql` replaces the five callers' bodies and runs `private.adopt_project_url()`, which, when `project_url` is missing, creates it from the address of the first of `assistant_function_url`, `screening_function_url` and `triage_function_url` present, then deletes those three; with none of the four present it changes nothing. It changes Vault rows, so it was not additive, and the rule then in force required the owner's approval before merge; #910's comment records that the owner approved it on 2026-11-11. **Revert:** `select private.revert_project_url();` and then `drop function private.revert_project_url();`, run once by the PM against production, restore the five bodies and the missing per-function secrets from `project_url`, which stays.
- Migration `20261105210000_assistant_photo_jobs.sql` changes no row of an existing table: it creates the bucket, its policies, the extension, the queue, the tables, the functions and the cron job, and replaces `private.assistant_tokens_today`. Since it changes what a message is allowed, steps now counting against the budget, it merges with the owner's approval ([`server.md`](server.md) §Edge Function deploys, "Gate").
- Migration `20261109230000_assistant_photo_retry_after.sql` ([ADR 0221](adr/0221-wait-a-refused-photo-read-s-retry-after-up-to-300-seconds-and-give-back-a-read-that-failed-before-it-was-sent-three-times-a-photo.md)) adds `not_sent` to the steps' outcomes and the argument above, replacing `finish_assistant_job_step`; it changes no row and what a read is charged is ADR 0219's. **Revert:** `select private.revert_assistant_photo_retry_after();` and then `drop function private.revert_assistant_photo_retry_after();`, run once by the PM against production before `revert_assistant_photo_charges()`; it puts the function back as the next migration below made it, and its `not_sent` steps become `model_error`. The `assistant` bundle goes back with it.
- Migration `20261109170000_assistant_photo_job_cleanup.sql` adds `assistant_jobs.photos_cleared_at` and the two functions above and replaces `next_assistant_job_step`, `finish_assistant_job_step`, `purge_assistant_jobs` and `sweep_assistant_jobs`; it changes no row. **Revert:** `select private.revert_assistant_photo_job_cleanup();` and then `drop function private.revert_assistant_photo_job_cleanup();`, run once by the PM against production before the two reverts below, put the four functions back and drop the two functions and the column. The `assistant` bundle goes back with it.
- **Revert.** `select private.revert_assistant_photo_jobs();` and then `drop function private.revert_assistant_photo_jobs();`, run once by the PM against production, unschedule the cron job, drop the functions, tables and queue and the bucket's policies, and put `assistant_tokens_today` back as `20261105090000_assistant_tokens.sql` made it. The bucket stays, since Storage refuses a delete of its objects in SQL: the PM empties and deletes it through the Storage API. It runs before `revert_card_form_skills()`, `revert_assistant_tokens()` and `revert_assistant()`, whose tables its tables reference. The `assistant` and `delete-account` bundles go back with it.
