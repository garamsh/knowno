# Server

The Supabase schema the app syncs to, and the extraction count, the plans and their versions with 스페셜, the assistant's prompts, configuration, daily token budget and message record, and the admin area's role, audit log, functions, suspensions and removals from sharing, the prompt store, each user's study settings and the media bucket beside it: its tables, row-level security, revisions, tombstones, account deletion, the migrations of stored vocabulary backs to senses blocks, of the plans to versions, of 무제한 grants to 스페셜, of the prompt labels into each plan's AI configuration and of every card's template to `free`, how migrations are named, previewed on synthetic data, and how they and Edge Functions reach production, and the tests that hold them.

## Current decisions

### Location and migrations

- The schema is defined by migrations in `supabase/migrations/`, applied in order: by the Supabase CLI's `supabase db reset` locally ([ADR 0010](adr/0010-server-schema-and-row-level-security.md)), and by Supabase's GitHub integration on the remote project.
- `supabase/seed.sql` holds no rows; the tests insert their own. Every `supabase start` loads it (`config.toml`, `[db.seed]`), and the database tests' fixtures assume an empty seed, so synthetic data goes in `supabase/preview-seed.sql` instead ([ADR 0111](adr/0111-preview-each-pull-request-s-migrations-on-synthetic-data-in-ci-and-keep-deploying-them-on-merge.md)).
- **Production data stays in production.** No copy of it is loaded into a local stack, a test, the preview or CI; the preview and the tests run on synthetic data alone, every user in it fictional.
- **Preview.** On a pull request touching `supabase/migrations/`, `.github/workflows/migration-preview.yml` runs `make preview-migrations`, which runs `scripts/migration-preview.ts` on a throwaway stack named `knowno_preview_<port>`, reserved and stopped as the test stacks are ([ADR 0111](adr/0111-preview-each-pull-request-s-migrations-on-synthetic-data-in-ci-and-keep-deploying-them-on-merge.md)):
  - it applies `main`'s migrations, loads `main`'s `supabase/preview-seed.sql`, records every table's columns and rows in `public`, `private` and `storage` with the functions of `supabase/migration-preview.sql`, and applies the migrations the pull request adds;
  - it writes the tables and columns added, dropped or altered, and per table the rows added, removed and changed, compared on the columns the table had before and still has, by the primary key it had; a value in an added column is not counted;
  - a migration of `main`'s that the pull request edits is listed and not applied, as the integration would not apply it again;
  - the job posts the report as its summary, holds no secret and is not a required check; it fails when a migration fails on the seeded data.
  - `main` is read as `scripts/check-migration-order.ts` reads it. The seed is `main`'s, which fits `main`'s schema, so a migration that makes `preview-seed.sql` invalid updates it in the same pull request.
  - `supabase/preview-seed.sql` puts rows in every table of `public` and `private` that the migrations leave empty, in the states the schema distinguishes: live and deleted decks and cards, public, copied and removed decks, each block type, reviews, card states, plans, extraction calls with a cursor, assistant messages recorded and not, an admin, a suspension, a 스페셜 grant and the backups.
- **Deploy path.** `main` is the deployed state. When a pull request adding a migration merges into `main`, Supabase's GitHub integration applies the migration to the production project; no one runs `supabase db push`. No approval gate holds it after merge, since the web and the Edge Functions deploy on merge too and a held database would leave them on the old schema ([ADR 0111](adr/0111-preview-each-pull-request-s-migrations-on-synthetic-data-in-ci-and-keep-deploying-them-on-merge.md)). Its `Supabase Preview` check on the merge commit records the run.
  - Measured: #115's merge `9b98292d2f642e794e5d32d969e3999629c5964b` at 13:55:55Z on 2026-10-16, with `Supabase Preview` running 13:56:27–13:56:35Z; #118's merge `a940deaef30ca376e34cd83631bd4112055cda6a` at 15:41:51Z, with the check 15:42:24–15:42:33Z. A `supabase db push` minutes after #115's merge reported "Remote database is up to date" (issue #117).
  - To confirm a migration reached production: the `Supabase Preview` check succeeded on the merge commit, and `supabase migration list --linked` lists the migration's version in its remote column.
- **Gate.** A pull request whose migration changes or deletes existing data merges only after the owner approves it, since merging deploys it; the PM asks with the reviewed pull request in hand. An additive migration needs no such approval, but it is deployed as merged, so it must be correct then. Workers make no change to the remote project.
- **Order.** The integration applies every migration file that the production project's migration history lacks. A file older than the latest applied migration "still runs and the step finishes with a warning" (Supabase's GitHub integration guide, `supabase/supabase` commit `626f0d412a5f88ef260289d4ed2b787f9705d6fc`, committed 2026-10-14, read 2026-10-18). Such a file runs after migrations that sort after it, in an order no local `supabase db reset` follows.
- **Naming.** A new migration's version, the 14 digits its name starts with, is later than every migration on `main`. A contributor names it from the current UTC time, as `supabase migration new` does, when that is later. Otherwise the contributor uses the latest version on `main` plus one second ([ADR 0048](adr/0048-name-each-new-migration-after-every-migration-on-main-and-check-it-in-make-lint.md)).
  - `scripts/check-migration-order.ts`, run by `make lint`, fails when a migration file that `main` lacks has a version not later than the latest on `main`, or a name not starting with 14 digits. It reads `main` as the first parent of a pull request's merge commit in CI, where the checkout of the ubuntu job running `make lint-code` fetches two commits deep, and as where `HEAD` left `origin/main` locally. It prints the number of new files and the base it compared with.
  - Branch protection on `main` requires branches to be up to date: `gh api repos/garamsh/knowno/branches/main/protection`, read 2026-10-18, returned `required_status_checks.strict: true` with the contexts `ci (ubuntu-latest)` and `ci (macos-latest)`, the CI jobs' names until #101 renamed them `ci (ubuntu)` and `ci (macos)`, which the PM sets as the required contexts when #101 merges. Of two pull requests that each pass the check against the same `main`, the second cannot merge until its branch is updated and the check runs again against the first.
  - Each required check is a final job of `.github/workflows/ci.yml` that fails when a job it waits on failed or was cancelled (#403). `ci (ubuntu)` waits on `make lint-repo` and on parallel jobs running `make lint-code format`, `test-app`, `test-db`, `test-sync`, `test-web`, `build-apk` and `build-ios build-engine-web`, which together run `make ci`; `ci (macos)` waits on `make build BUILD=ios`. A pull request whose changed files all lie under `docs/` or end in `.md` skips every job but `make lint-repo`, and both checks pass; a push to `main` runs only the jobs that save caches, `make lint-code format`, `test-app`, `test-sync`, `build-apk`, `build-ios build-engine-web` and `make build BUILD=ios`, and only when it changed a file their cache keys are computed from. Neither required check runs on it.
  - `scripts/check-migration-order_test.ts`, run by `make test-db` through `scripts/deno.ts`, runs the check on repositories it builds in a temporary directory. It covers a merge commit cloned two commits deep, as CI checks one out, and a branch beside `origin/main`.

### Edge Function deploys

- **Deploy path.** When a pull request changing a function under `supabase/functions/` merges into `main`, Supabase's GitHub integration deploys it to the production project; no one runs `supabase functions deploy`. It deploys the functions `supabase/config.toml` declares under `[functions.<slug>]`, `extract-cards`, `delete-account`, `mcp` and `assistant`, and uploads one only when its bundle or its JWT verification setting changed. A function's bundle includes the files of `supabase/functions/_shared/` it imports, so a change there deploys every function importing the changed file: `auth.ts` all four, the card tools `mcp` and `assistant`, `keys.ts` `extract-cards` and `assistant`.
  - Source: Supabase's GitHub integration guide, `apps/docs/content/guides/deployment/branching/github-integration.mdx` in `supabase/supabase` at commit `626f0d412a5f88ef260289d4ed2b787f9705d6fc`, committed 2026-10-14, read 2026-10-18. Under "Deploying changes to production" it lists "Edge Functions declared in `config.toml` are deployed"; under "Edge Functions" it says "A function is uploaded again only when it changed."
  - Measured: #169's merge `5ab5440e4475237dc21f25911a4d9f52ab89c3a1` at 19:20:11Z on 2026-10-17 changed, under `supabase/`, only files in `supabase/functions/extract-cards/`. Its `Supabase Preview` check ran 19:20:38–19:20:47Z. On 2026-10-18, `supabase functions list` showed `extract-cards` at version 9, updated 19:20:46 UTC, and no one had deployed it by hand (issue #177).
  - To confirm a function reached production: the `Supabase Preview` check succeeded on the merge commit, and `supabase functions list` shows the function updated during that check.
- `mcp` runs with `verify_jwt = false`, so its 401 challenge and its protected resource metadata reach a client without a token; it verifies every MCP request's token itself and takes one optional secret beyond the platform's `SUPABASE_URL` and `SUPABASE_ANON_KEY`, `MCP_PUBLIC_URL`, the public URL it advertises ([`mcp.md`](mcp.md)).
- **Secrets.** The integration sets only the function secrets `config.toml` declares under `[edge_runtime.secrets]` (the same guide: "The step saves the function secrets declared under `[edge_runtime.secrets]`"), and `config.toml` declares none, and the functions read no provider secret: every provider key is in Vault (§AI providers). A secret is set by hand on the production project by the owner or the PM; a merge changes none of them.
- **Gate.** A pull request changing a function merges only after the owner approves it when the change:
  - needs a secret the production project lacks, or a new value of one, which the owner or the PM sets before the merge, since the deploy the merge makes would otherwise run without it;
  - changes which model is called, or otherwise the cost of a call, since cost is the owner's.
  The PM asks with the reviewed pull request in hand. A prompt change on the same model ships as merged after the PM's review, with the eval as its evidence where one applies. A response the apps in use cannot read is not merged ([ADR 0051](adr/0051-extract-each-card-with-a-question-a-fullest-and-a-short-answer-and-a-detail-step-and-eval-notes-pages-by-terms.md)). Every other function change is deployed as merged, so it must be correct then. Workers make no change to the remote project.

### Tables

- `public` holds `decks`, `cards`, `reviews` and `card_states`, mirroring the app's local tables (`app/lib/database/database.dart`). Their ids are created on the device.
- `decks`, `cards` and `reviews` have `id` as primary key; `card_states` has `(user_id, card_id)`.
- Every synced id, and every column that references one, is `uuid`: `decks.id`, `cards.id`, `cards.deck_id`, `cards.origin_deck_id`, `reviews.id`, `reviews.card_id`, `card_states.card_id`, `deck_reports.deck_id` and `deck_copies.deck_id`. No id column has a default, so a row sent without an id is refused. `extraction_usage.id` is an identity ([ADR 0034](adr/0034-key-synced-rows-by-client-made-uuids-purge-tombstones-past-a-revision-horizon-and-index-each-query.md)).
- Migration `20261016180000_uuid_keys.sql` cast those columns from `text` in place, so every row kept its id. It first raises, changing nothing, unless every value is in canonical lowercase form, the only form Postgres returns unchanged, so the phone, which keeps ids as text, holds the same id the server returns ([`sync.md`](sync.md)). In one transaction it dropped the five foreign keys and the two policies that name those columns, cast them, and recreated the keys, the policies, `list_public_decks` and `record_deck_copy`.
- PostgREST sends a uuid as the same JSON string a text id was, so app and web versions released before the conversion keep working.
- The app and the web create new ids as version 7; rows created before keep their version 4 ids, and nothing reads the version ([`sync.md`](sync.md)).
- Every row carries `user_id`, referencing `auth.users` with `on delete cascade`, so deleting an account deletes its rows. It defaults to the caller's `auth.uid()`.
- A card's `front` and `back` are `jsonb` arrays of blocks, in the encoding the app stores ([`deck.md`](deck.md)); a value that is not an array is refused.
- `cards.source` and `reviews.rating` take the local tables' values: `manual`, `import` or `copy`, and `again` or `good`. Migration `20261015180000_public_decks.sql` widened the source check to a copied card's value in one statement, changing no row ([ADR 0020](adr/0020-public-decks-in-a-sharing-domain.md)).
- `decks.icon` and `decks.color` are a deck's appearance keys, nullable, each bounded to 40 characters and checked against no list, so a newer app's keys sync; a client draws the default for a key it does not know. `authenticated` inserts and updates them as the deck's other columns. Migration `20261026120000_deck_appearance.sql` added them and their grants, changing no row ([ADR 0103](adr/0103-give-each-deck-an-icon-and-a-colour-stored-as-two-unchecked-keys-and-drawn-on-its-tile-in-place-of-the-initial.md)).
- `decks.image_media_id` is the media id of a deck's image, nullable, with no foreign key, since a device pushes the deck before its file's row lands (§Media storage). `authenticated` inserts and updates it as the deck's other columns.
- `cards.origin_deck_id` is a copied card's source deck, with no foreign key, since that deck is another user's.
- `cards.template` and `cards.template_version` are the template a card was made from and its version, nullable, so a card from before holds neither until an app's next write fills them in. The template is checked against no list, so a newer app's template syncs; the version is at least 1. `authenticated` writes both through the table's grants. Migration `20261026130000_card_template.sql` added them and rewrote no row ([ADR 0106](adr/0106-store-each-card-s-template-and-each-block-s-version-and-id-derive-one-face-or-front-back-from-blanks-and-keep-unknown-shapes-unchanged.md)); migration `20261027140000_card_template_free.sql` made every live card's template `free` (§Card template migration).
- `reviews.fuzz_factor` is the review's fuzz factor ([ADR 0012](adr/0012-fuzz-review-intervals.md)), null for a review scheduled without fuzz, and checked to `[0, 1)`. Migration `20261015120000_review_fuzz_factor.sql` added it.

### Public decks

- `decks.visibility` is `private` (the default) or `public`; a public deck has `published_at`. `decks.description` is at most 300 characters. These sync like the deck's name ([`sharing.md`](sharing.md)).
- `decks.hidden` and `decks.copy_count` are the server's: clients read them and cannot write them.
- `public.profiles` holds one display name per user, 2 to 20 characters with no surrounding whitespace. Users insert and update their own; anyone signed in reads the name of a user with a visible public deck.
- `public.deck_reports` holds one report per reporter and deck, with a reason: `inappropriate`, `spam`, `copyright` or `other`. A user inserts a report only as itself, on a visible public deck of another user, and reads none back.
- A trigger hides a deck once three distinct users reported it, under an advisory lock on the deck seeded with 2, so concurrent reports are counted one after another. The lock's key hashes the deck's id as text, so the key a deck took before the ids were `uuid` is the key it takes now. An admin unhides it in the web admin area, which can also make a deck private and dismiss its reports (§Admin area).
- `public.user_blocks` holds a user's blocks; users select, insert and delete their own.
- `list_public_decks(search, sort, page_size, page_offset)` runs as the caller and lists visible public decks not of a user the caller blocked, whose name or description holds the search ignoring case, newest first or most copied first, with the owner's display name and live card count. It returns each deck's id as `uuid`.
- `record_deck_copy(deck_id uuid)` runs as its owner: it returns false for a deck that is not visibly public, and otherwise true. A caller's first copy of a deck it does not own inserts a row in `public.deck_copies` and adds one to `copy_count`; a later copy by that caller, or a copy by the owner, changes neither (issue #67).
- `public.deck_copies` holds one row per deck and user who copied it, keyed by the two, so concurrent copies by one user insert one row and add one between them. Clients hold no privilege on it, and row-level security is on with no policy. Removing a row, with its deck or its account, leaves `copy_count` as it is.
- Copies made before the table existed were not recorded per user, so their counts stay as they were and later copies add to them. Migration `20261016090000_deck_imports.sql` is additive: it creates the table and replaces the function with the same signature, changing no row.
- Migration `20261019230002_name_public_deck_copies.sql` named copying a public deck "copy" ([ADR 0082](adr/0082-name-copying-a-public-deck-copy-and-keep-import-for-photo-import.md)): it renamed `deck_imports` to `deck_copies` with its keys and index, `decks.import_count` to `copy_count` with its check, and `record_deck_import` to `record_deck_copy`, recreating `list_public_decks`, `admin_public_decks`, `admin_deck` and `admin_user_deck`, which return the count, with the same bodies and privileges. It changed each copied card's `source` from `shared` to `copy`, so each such row took a new revision, its edit time kept; no other row changed.
- A deck is visibly public when it is public, not hidden and not deleted.

### Sync columns

- `updated_at` — the device's edit time, set by the client; #24 orders concurrent edits by it. `updated_at`, `created_at`, `reviewed_at` and `deleted_at` are the client's. The app's sync sends them at millisecond precision, as stored in schema v6, and so does the web.
- `deleted_at` — a tombstone on `decks` and `cards`, null while the row is live. Sync never deletes a row.
- `reviews` and `card_states` have no tombstone, since nothing writes one ([ADR 0077](adr/0077-drop-the-review-and-card-state-tombstones-that-nothing-writes.md)). Migration `20261019230000_drop_review_state_tombstones.sql` dropped their `deleted_at`, the `reviews_delete` policy, `card_states_tombstone_revision` and `reviews_live_user_id_reviewed_at`, created `reviews_user_id_reviewed_at` in its place, and rewrote every function that filtered on the column without that filter.
  - It drops each column only after `private.require_no_tombstone(table)` finds no row with it set, raising and changing nothing otherwise, so no row changes. The function stays, so its refusal is tested.
- `revision` — set on every insert and update by a trigger, from the one sequence `private.revision` shared by all four tables. Whatever the client sends is overwritten. Each table is indexed on `(user_id, revision)`, the pull cursor.
- Before drawing, the trigger takes a transaction-level advisory lock keyed by a 64-bit hash of the row's `user_id`, held until commit. One user's writing transactions therefore run one after another, so for each user a later commit holds the higher revision, and a pull by revision cannot pass a row that commits later. Different users never wait on each other, except on a hash collision ([ADR 0010](adr/0010-server-schema-and-row-level-security.md)).
- The cost: one user's concurrent writes, from two devices or two requests, serialize.
- The sequence and the trigger function live in the schema `private`, which the API does not expose. The function runs as its owner, so clients need no privilege on the sequence and have none.

### Access

- `anon` holds no privilege on the four tables; every statement it sends is refused.
- `authenticated` may select, insert, update and delete in `cards` and `card_states`, and select and delete in `decks`. On `decks` it may insert and update every column but `hidden` and `copy_count`.
- `reviews` is insert-only for `authenticated`, except `rating` and `updated_at`, which a toggle changes ([ADR 0007](adr/0007-study-swipe-screen-and-session-toggle.md)). A client inserts `fuzz_factor` with its review and never changes it. A client cannot delete a review; a review goes only with its account, through the `auth.users` cascade.
- Row-level security is on for all four tables, with one policy per command a client may run, allowing only rows where `user_id = auth.uid()`; `reviews` has none for delete.
- The one select policy of `decks` and of `cards` also lets any signed-in user read a visibly public deck and its live cards, and that of `profiles` the name of a user with one. Each tests the owner's condition first and ORs in the public one, so a read of one's own rows never runs the public condition's subquery ([ADR 0034](adr/0034-key-synced-rows-by-client-made-uuids-purge-tombstones-past-a-revision-horizon-and-index-each-query.md) §7). Migration `20261016200000_checks_and_policies.sql` merged each table's former owner and public pair into it, changing no row's visibility. Writes stay the owner's, since no write policy names another user's rows.
- Every policy names `to authenticated` and reads `(select auth.uid())`. A pull therefore filters on its account's `user_id` ([`sync.md`](sync.md)).
- The privileges are granted in the migration, not left to the project's default privileges.
- `record_deck_copy` runs as `security definer` and `authenticated` may execute it, which the Security Advisor reports as lint `0029_authenticated_security_definer_function_executable`. That is intended: it writes `deck_copies` and `copy_count`, which no client may write, and [ADR 0034](adr/0034-key-synced-rows-by-client-made-uuids-purge-tombstones-past-a-revision-horizon-and-index-each-query.md) §7 lists it among the `security definer` functions, granted to the one role that calls it (issue #113).
- The app does not use the service role, and neither does the web or the `mcp` function, which reads and writes with the caller's token ([`mcp.md`](mcp.md)): the admin area reads and writes through the functions of §Admin area with the user's session.

### Extraction usage

- `public.extraction_usage` holds one row per photo extraction the `extract-cards` function let through: an identity `id`, `user_id` referencing `auth.users` with `on delete cascade`, and `created_at` ([`ai-extraction.md`](ai-extraction.md), [ADR 0013](adr/0013-extract-cards-function-and-eval.md)).
- It is not synced: it has no revision, tombstone or edit time.
- `authenticated` may only select it, and row-level security allows only the caller's rows, so the app can read today's count. `anon` holds nothing.
- Rows are written only by `public.begin_extraction(user_id)`, which the function calls (§Prompt store), executable only by `service_role`. It takes a transaction-level advisory lock on the user, counts the rows since the start of the period of the user's plan version (§Plans), and inserts one under its limit, or whatever the count for a user on 스페셜 (§Plans, "스페셜"). `service_role` itself may not insert directly. Migration `20261019230001_drop_old_function_entry_points.sql` dropped `public.consume_extraction` and `public.start_extraction`, which only a function deployed before plans or the prompt store called, changing no row ([ADR 0078](adr/0078-keep-no-older-app-or-function-build-working-until-the-first-store-release.md)).
- The lock's key is the hash of the user id seeded with 1, never the revision lock's seed 0.
- `public.extraction_allowance()`, `security definer` and executable only by `authenticated`, returns the caller's `photo_limit`, null for a caller on 스페셜 (§Plans, "스페셜"), and naming no plan, its `period` (`month` or `day`) and `used`, the caller's rows since the period's start, read from `auth.uid()` with no user argument, so the app can say before reading several photos how many the period leaves ([`ai-extraction.md`](ai-extraction.md), [ADR 0089](adr/0089-import-up-to-ten-photos-into-one-list-read-two-at-a-time-and-state-today-s-limit-before-reading.md), [ADR 0097](adr/0097-give-each-plan-versions-of-its-terms-with-a-start-free-10-a-month-pro-100-a-day-and-max-unlimited-to-1000-a-day-each-grant-taking-the-latest-at-its-monthly-renewal.md)). It resolves the version through `private.entitlement_of` and counts the same rows from the same start as `begin_extraction`, so the two agree; it takes no lock and writes nothing. Migration `20261019234136_extraction_allowance.sql` added it, changing nothing that existed, and `20261026005136_plan_versions.sql` replaced it with these columns.
- The migration adding it is additive: it creates the table, its index and the function, and changes nothing that existed.

### Admin area

- The admin role is the table `private.admins`, one row per admin with who granted it and when; a user without a row is not an admin ([ADR 0070](adr/0070-run-the-service-from-a-web-admin-area-whose-role-and-audit-log-live-in-the-database-and-whose-every-read-and-write-is-checked-there.md)). It sits in `private`, which the API does not expose, and no client role holds a privilege on it, so no email, id or list in code or configuration names an admin.
- The first admin is a row the PM inserts on the production project after the migration deploys: `insert into private.admins (user_id) select id from auth.users where email = 'sauce@garam.sh';`. Every later grant and revoke goes through the admin area.
- `private.admin_audit` records every admin write: the admin's id, set null when that account is deleted so the row stays, and a snapshot of the email, a snake-case `action` and `target_kind`, a `target_id`, a JSON `detail` object and the time. The writing function names the action; a later one adds its own names with no schema change.
- Every admin read and write is a `security definer` function in `public` with an empty `search_path`, executable by `authenticated` and not `anon`. Each first calls `private.require_admin()`, which raises `42501` unless the caller has a row in `private.admins`, and each write records itself through `private.audit()` in its transaction. A write that changes nothing records nothing. `public.is_admin()` answers the caller's role.
- The functions: `admin_overview` and `admin_extractions_by_day` (users, study and extractions per UTC day); `admin_reported_decks`, `admin_public_decks`, `admin_deck` and `admin_deck_cards` (a deck is readable only when public or reported); `admin_find_users` and `admin_user`; `admin_admins` and `admin_audit_log`; and the writes `admin_set_deck_hidden`, `admin_unpublish_deck`, which sets the deck private with an edit time of now so the owner's devices pull it, `admin_dismiss_reports`, which leaves a hidden deck hidden, `admin_grant_admin` by an existing user's email, and `admin_revoke_admin`, which refuses the caller's own role and runs one at a time under an advisory lock seeded with 3, checking the caller's role again once the lock is held, so two admins revoking each other at once cannot leave none.
- The overview's counts across users scan the reviews in range and `extraction_usage` without an index of their own; the PM adds one when `supabase inspect db outliers` lists either function among the ten statements of highest total time.
- Migration `20261019120000_admin.sql` is additive: it creates the two tables, their indexes and the functions, and changes no existing row or object.

### Plans

- The plans are Free, the default, Pro, Max and 스페셜 ([ADR 0097](adr/0097-give-each-plan-versions-of-its-terms-with-a-start-free-10-a-month-pro-100-a-day-and-max-unlimited-to-1000-a-day-each-grant-taking-the-latest-at-its-monthly-renewal.md), superseding [ADR 0071](adr/0071-give-each-user-a-plan-whose-model-and-daily-limit-an-admin-sets-in-the-database-and-make-one-model-call-per-photo.md)'s plans set in place; [ADR 0177](adr/0177-make-unlimited-use-the-plan-special-that-no-user-sees-put-every-admin-on-it-and-move-each-unlimited-grant-onto-it.md)). - `private.plan_versions` holds each version of a plan's terms: the plan, `free`, `pro`, `max` or `special`; the `quota`, `monthly`, `daily`, `unlimited` or `none`; an `amount` from 0 to 100,000, a month's or a day's photos, or for `unlimited` the fair-use cap a day, and none for `none`; `starts_at`; `applies_to_all`; and who created it when.   - one begun before it is on the version in effect at that renewal, `private.plan_version_at(plan, renewal)`, the latest started by then;
  - a Free user is on Free's version in effect at the later of its sign-up and the last renewal;
  - an admin is on 스페셜's version, whatever it was granted;

- **In the users' favour.** `private.in_favour` holds a version's terms against every version of its plan started by its start: a quota no more generous in the order monthly, daily, unlimited, and an amount no larger. Only such a version may apply to all. A version holds no model: the plan's model is its AI configuration's (§AI providers).

- `public.begin_extraction(user_id, configuration_id)` (§Prompt store, §AI providers) resolves the user's version, its `photo_limit` and `period`, and whether the photo is allowed, recording it when it is, under the extraction lock (§Extraction usage). ### Integrity

- A card's deck, and a review's or card state's card, belong to the row's own user. Composite foreign keys enforce it: `cards (user_id, deck_id)` references `decks (user_id, id)`, and `reviews` and `card_states` reference `cards (user_id, id)`, each with `on delete cascade`.

### Checks

- Besides the column checks above, five checks hold on every row ([ADR 0034](adr/0034-key-synced-rows-by-client-made-uuids-purge-tombstones-past-a-revision-horizon-and-index-each-query.md) §5):
  - `decks_name_check`: `deleted_at is not null or name <> ''`;
  - `cards_card_key_check`: `deleted_at is not null or card_key <> ''`;
  - `card_states_stability_check`: `stability >= 0.001`;
  - `card_states_difficulty_check`: `difficulty between 1 and 10`, the engine's clamps with the one above;
  - `cards_origin_deck_id_check`: `(source = 'copy') = (origin_deck_id is not null)`.
- A tombstone may have an empty name or card key, since the purge strips them.
- Migration `20261016200000_checks_and_policies.sql` added them. It first counts each check's failing rows and raises, changing nothing, unless every count is zero. It then adds each `not valid` and validates it, in the same transaction, so the lock the addition takes lasts to commit. A table large enough for that lock to matter is validated in a later migration.
- **Constraint names.** Constraints keep Postgres's default names (`_pkey`, `_key`, `_fkey`, `_check`), and a constraint added later is given its name explicitly in that form.
- A row a check refuses fails a sync run as `SyncFailed` ([`sync.md`](sync.md)).

### Horizon and watermark

- `private.sync_horizon` holds one row: the revision the last tombstone purge purged below, 0 until a purge runs ([ADR 0034](adr/0034-key-synced-rows-by-client-made-uuids-purge-tombstones-past-a-revision-horizon-and-index-each-query.md) §3).
- `public.sync_horizon()` returns one row to the caller: `horizon`, that revision, and `watermark`, the last value of `private.revision` read after taking the caller's revision lock, the advisory lock the revision trigger takes ([ADR 0041](adr/0041-raise-each-pull-cursor-to-a-watermark-read-under-the-user-s-lock-and-strip-local-tombstones-in-place.md)).

### Tombstone purge

- A `pg_cron` job, `purge-tombstones`, runs `private.purge_tombstones()` daily at 18:00 GMT, 03:00 in Korea ([ADR 0034](adr/0034-key-synced-rows-by-client-made-uuids-purge-tombstones-past-a-revision-horizon-and-index-each-query.md) §3). Each run:
  - records the revision sequence's last value in `private.revision_marks`, with the server's time;
  - deletes `cron.job_run_details` rows that ended more than 30 days earlier;
  - purges the `decks` and `cards` tombstones whose `revision` is at or below the latest mark taken 90 days or more earlier, and stores that mark as the horizon in `private.sync_horizon`, which `sync_horizon()` returns ([`sync.md`](sync.md));
  - deletes the marks older than that one.
  - With no mark 90 days old, a run purges nothing and the horizon stays where it is. The first purge therefore comes 90 days after the first mark.
- Study history survives deletion (the owner's decision, issue #93):
  - a card tombstone that no review references is deleted, with its card state;
  - one that reviews reference keeps its row, stripped: `front` and `back` become `[]` and `card_key` `''`, so its reviews stay in the streak and the statistics;
  - a card state stays with its card's row, stripped or live, and goes with the row;
  - a deck tombstone is deleted once no card row references it, with its reports and its users' copy records, which cascade from it. Until then it keeps its row, stripped of its name and description and made private.
  - A strip is an update, so the row takes a new revision and devices pull it. A row already stripped is not updated again.
  - Only account deletion removes reviews and the kept rows.
- A run that purges first locks `cards` and `reviews` in `share row exclusive` mode until it commits. A write to either waits, so no review or card written during the run comes to reference a tombstone the run deletes ([ADR 0053](adr/0053-purge-tombstones-before-any-store-release-enable-pg-cron-in-the-purge-s-migration-and-lock-cards-and-reviews-while-it-purges.md)). A run with no mark 90 days old takes no lock.
- `private.purge_tombstones()` runs as its owner and sets `search_path = ''`; `execute` is revoked from `public`, `anon` and `authenticated`.
- Migration `20261018090002_tombstone_purge.sql` added the marks table, the function and the job. It deletes no row itself.
  - It first calls `private.check_purge_start()`, which raises, changing nothing, unless `pg_cron` is in `pg_available_extensions` and `shared_preload_libraries`, `private.sync_horizon` holds its one row at 0, and no job named `purge-tombstones` exists. The function stays, so its refusals are tested.
  - It then runs `create extension if not exists pg_cron with schema pg_catalog`. **Merging it enables `pg_cron` in production if it is not on yet**; where the owner enabled Cron first, the statement does nothing.
- **Order.** The purge was built before any store release, by the owner's decision of 2026-10-18 in issue #108, which supersedes ADR 0034 §9's order of building it after the app's store release ([ADR 0053](adr/0053-purge-tombstones-before-any-store-release-enable-pg-cron-in-the-purge-s-migration-and-lock-cards-and-reviews-while-it-purges.md)). The only client devices then were the owner's, running `main`'s build, which reads the watermark.
- **Runs.** `cron.job_run_details` records each run, so a failure or a missing day shows there; a horizon that stops rising shows through `sync_horizon()`.

### Card frame migration

- Migration `20261102120000_card_frame.sql` moves every live card of `free` at version 1, or of none or of `flip`, `cloze` or `table` at version 1, to the 칸 frame: its 칸 list in `front`, `[]` in `back`, `free` at version 2 ([`deck.md`](deck.md), [ADR 0137](adr/0137-frame-a-card-by-its-blocks-each-block-type-deciding-whether-it-has-a-front-and-a-back.md), [ADR 0140](adr/0140-keep-every-back-that-differs-from-the-filled-text-show-a-back-blank-beside-a-front-blank-after-the-answer-and-keep-a-front-word-s-meanings-first.md), #549). It changes existing data; the PM approved it under the owner's goal on 2026-11-02, on the dry run of 4,038 live cards recorded on #488, which `supabase/card-frame-dry-run.sql` re-runs read-only before the merge.
- `private.card_frame` holds the rule, `cellsFromSides`' and the fixtures' in `supabase/fixtures/card-frame/`, and returns null for a card it leaves.
  - It leaves a block of a type or version no build wrote, as the dry run counts them.
  - It also leaves two cases the dry run does not count: a block breaking a field the rule reads, and a card it would give a 글 of no text, which `decodeCells` refuses. The app converts such a card on read. The migration's notice names how many it left.
- `private.migrate_card_frame()` converts, and the migration calls it once.
  - It holds `public.cards` in `share row exclusive` mode from before it reads a row until commit, so the row backed up is the row replaced and no writer holding a user's revision lock waits on one of its rows. Reads go on. At 5,000 cards it took about 2 s on the test stack, inside the 8 s of `authenticated`'s statement timeout that bounds a writer's wait.
  - It copies each changed row into `private.card_frame_backup` first: `card_id`, `user_id`, `front`, `back`, `template`, `template_version`, the `front` it wrote as `written`, and `migrated_at`. That table enables row-level security with no policy and grants nothing to `anon` or `authenticated`, so no client reads it. A row goes with its card's delete, so with its account. A later migration drops the table once the owner closes the window.
  - A back exactly equal to the filled text drops from the card and stays in the backup. Every other back is kept.
  - A second run converts nothing, since `free` v2 is not among the templates it reads. A tombstone, a card already in the frame, and a template or version no build wrote are left alone.
- **How it reaches devices.** The update draws a new `revision` through the trigger, so every device pulls the card, which keeps its `card_key` and `updated_at`. Each device's schema step 14 makes the same change in its own rows ([`sync.md`](sync.md)):
  - a device holding the card synced takes the server's copy on the tie;
  - a device with an edit not yet pushed wins the tie as an unsynced row, or holds a later `updated_at`, so its edit is pushed over the migration's, in the frame after step 14 and at v1 on a build without it.
  - No review or card state changes.
- **Revert.** `select private.revert_card_frame();`, run by the PM against production and again until no device writes the frame, returns how many cards it changed. It runs before any earlier app build is reinstalled, since that build opens a `free` v2 card read-only.
  - A backed-up live card still as the migration wrote it takes back its `front`, `back`, `template` and `template_version` exactly.
  - Any other live card at `free` v2, written in the frame before or after the migration, takes the projection of `sidesOf` at `free` v1, through `private.card_frame_parts`: every part shown before the reveal on the front, every part added by it on the back, a 칸 with blanks or of an unknown shape on the front as it is stored.
  - Each takes a new revision and keeps `card_key` and `updated_at`. A tombstone stays, and so does a card a build has since written outside the frame.
- Every function revokes `execute` from `public`, `anon` and `authenticated`, and runs as `security invoker`: only the migration and the PM call them.

- `make test` runs `scripts/test-db.ts`. Where Docker answers, it starts a throwaway stack of its own with only Postgres, which applies the migrations, runs the tests and prints their count ([ADR 0014](adr/0014-database-tests-on-a-stack-of-their-own.md)). Where Docker does not, it prints that the tests were skipped and why.
- The throwaway stack is named `knowno_test_<port>` and publishes its database on the first port in 54400–54499 that the run reserves under `${TMPDIR:-/tmp}/knowno-test-db/` and that nothing listens on. Concurrent runs, from several checkouts on one host, each get their own, and none touches the `knowno` stack or its rows.
- The script stops its stack, deleting its data, on every exit, interrupts included, and retries a stop that fails because another stack is stopping at the same moment. A stack it cannot stop fails the run, which prints how to remove it. A run killed with `SIGKILL` leaves its stack and reservation behind, to remove by hand.
- That reservation and that stop are defined once, in `scripts/stack.ts`, which `scripts/test-sync.ts`, `scripts/test-web.ts` and `scripts/migration-preview.ts` import as well, so their stacks reserve under the same directory and stop the same way.
- `scripts/test-migration-preview.ts`, run by `make test-db`, runs the preview on a repository it builds in a temporary directory: `main` holds this repository's migrations and preview seed, and a merge commit adds a fixture migration and edits one of `main`'s. It checks that the seed fills every table of `public` and `private`, that each column and table added, dropped or altered and each row updated or deleted is reported, that a table left alone reports no change, as control, and that the edited migration is listed and not applied.
- CI's ubuntu jobs install the Supabase CLI and run them: the database tests, the senses dry-run test, the migration preview test and the Deno tests in the `make test-db` job, the stack tests in `make test-sync`, the web e2e spec in `make test-web`. Each job runs on a runner of its own, so their stacks start in parallel; within a job each script still starts and stops its own.
- `make test` then runs `scripts/test-sync.ts`, the two-device sync test, the sharing server test and the suspension test against a throwaway stack with Auth and PostgREST ([`sync.md`](sync.md), [`sharing.md`](sharing.md), [`account.md`](account.md)).
