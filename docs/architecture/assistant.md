# Assistant

The `assistant` Edge Function, 말랑이 as an assistant that builds notes and cards with the user in conversation: its requests, the stream, the tool loop and its limits, the tools, the card forms it reads, proposals and their commit, the photo jobs that read the chat's photos in the background, how each provider is called with its web search and reasoning, the per-plan configuration and daily token budget it reads, an admin's draft saved after a check call, its log and its tests. The schema behind the configuration and the budget is [`server.md`](server.md)'s; the card tools it shares are [`mcp.md`](mcp.md)'s; the app's chat screen is [`assistant-app.md`](assistant-app.md)'s, and the web's is [`web-assistant.md`](web-assistant.md)'s.

## Current decisions

### Location

- `supabase/functions/assistant/` is a Deno module with no third-party dependency: it calls Supabase Auth, PostgREST and the provider of the caller's plan with `fetch` ([ADR 0190](adr/0190-serve-the-assistant-from-an-edge-function-that-streams-a-tool-loop-proposes-cards-in-groups-and-commits-what-the-user-checks-under-a-per-plan-daily-limit.md)).
- It imports the card tools from `supabase/functions/_shared/` (`tools.ts`, `store.ts`, `input.ts`, `cards.ts`) and the card forms (`card_forms.ts`), as `mcp` does, and Vault's key read, `_shared/keys.ts`, as `extract-cards` does.
- `index.ts` is its composition site: it reads the configuration once and passes `fetch`, the keys, the card forms' reader, the logger, the clock, the random source, the address lookup and the timeout to the handler.
- `config.toml` sets `verify_jwt = true`; the function then asks Supabase Auth for the token's user with the service-role key, refusing the anon key and an anonymous sign-in, as `extract-cards` does. It reads `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY`, which the platform sets, and no other secret.
- Merging a change to it deploys it ([`server.md`](server.md) §Edge Function deploys).

### Requests

- `POST /functions/v1/assistant`, a message, with the user's token and a JSON body that holds at most 512 KiB (`MAX_BODY_BYTES`) once its assistant turns are shortened, read up to `MAX_REQUEST_BYTES`, 512 KiB beside 40 turns each a longest reply of three-byte characters, so the server's own history is never refused for its size ([ADR 0195](adr/0195-meter-the-assistant-by-a-daily-token-budget-per-plan-charged-when-a-message-ends-shorten-a-resent-reply-and-save-a-draft-after-a-check-call.md)):
  - `messages` — 1 to 40 turns, oldest first, the last the user's: `{role: "user", text, photos?}` or `{role: "assistant", text, proposals?, choice?, job?}`. A user turn's `photos` are 1 to 50 distinct ids of photos it uploaded to `assistant-photos` (§Photo jobs), read by the model as `[n photos attached]`; an assistant turn's `job` is the `job` event it showed, `{id, photos}`, read as `[photo job <id> started over <n> photos]`. A user turn's text is at most 4,000 characters (`MAX_TURN_TEXT`); an assistant turn's longer text, such as a long reply the server streamed, is shortened to that length, its head and tail around a marker counting the characters left out, and never refused ([ADR 0195](adr/0195-meter-the-assistant-by-a-daily-token-budget-per-plan-charged-when-a-message-ends-shorten-a-resent-reply-and-save-a-draft-after-a-check-call.md), #746). An assistant turn's `proposals` are the proposals it showed, as the stream sent them, and its `choice` the question it asked; the model reads them after the turn's text, each proposal with its ids and each group's first five fronts, each cut to 80 characters. A turn so described is at most 16,000 characters (`MAX_DESCRIBED_TURN`): past it, its proposals show one front a group, then none, then only their sizes, and then those that still do not fit are counted, so a turn the server sent always fits; a turn whose text and question alone are over it is refused.
  - `context` — optional `{deck_id}`, the note the chat was opened in; the model is told its name and id when it is the user's live note.
- `POST /functions/v1/assistant/commit` — `{proposal, checked}`, where `checked` maps each group's id to the ids of its cards to write (§Commit).
- `POST /functions/v1/assistant/settings/configuration` — an admin's draft (§Draft).
- `GET /functions/v1/assistant/jobs/{id}` and `POST /functions/v1/assistant/jobs/{id}/cancel` — a photo job's poll and cancel, and `POST /functions/v1/assistant/jobs/work`, the worker, called with the service-role key alone (§Photo jobs).
- A message or commit is checked in this order: route, method, configuration, token, user, body size, JSON, for a message what the body holds once its replies are shortened, suspension, then for a message its turns, the card forms (§Card forms) and the start. A refused message never reaches the model, and one refused before the start is not recorded.
- Every refusal of a message or commit is `{error}`, and the commit's `400` and `422` add `message`:

| Status | Code | When |
|---|---|---|
| 400 | `bad_request` | the body is not JSON, or not a message or commit of the forms above |
| 401 | `unauthenticated` | no bearer token, an invalid one, the anon key, or an anonymous sign-in |
| 403 | `suspended` | an admin suspended the user |
| 404 | `not_found` | a path other than the function's, or a job that is not the caller's |
| 405 | `method_not_allowed` | a method other than `POST`, or than `GET` for a job's poll |
| 413 | `too_large` | a commit body over 512 KiB; a message body over `MAX_REQUEST_BYTES`, or holding over 512 KiB once its assistant turns are shortened |
| 422 | `refused` | the commit's write tool refused it whole, such as a note that is not the user's |
| 429 | `rate_limited` | the day's tokens charged have reached the plan's budget; the body adds `token_budget` and `tokens_used` |
| 429 | `busy` | another message of the user is still running, as one is until its call ends after its client cancelled it; the client retries after a few seconds |
| 503 | `not_configured` | a platform variable is missing, or the plan has no configuration or budget |
| 503 | `unavailable` | the configuration's provider has no key in Vault, the message not recorded; or Supabase did not answer, the card forms included |

### Stream

- A started message is answered `200` with `text/event-stream`, each event `event: <name>` and one line of JSON `data`:
  - `text` — `{delta}`, 말랑이's text as it arrives;
  - `citation` — `{url, title}`, a web source the reply cites, once per URL a message;
  - `proposal` — a proposal (§Proposals), whole, sent again whole under the same id when one of its groups is remade;
  - `choice` — `{prompt, options}`, a question with 2 to 6 options; the client sends the pick, or a typed answer, as the next user turn;
  - `job` — `{id, photos, status: "running"}`, a photo job started; the client polls it and sends it back on its assistant turn (§Photo jobs);
  - `error` — `{error: "model_error"}` when a model call failed, or `{error: "cut"}` when a reply stopped at the output limit;
  - `usage` — always last, sent once the message is charged: `{outcome, model_calls, input_tokens, output_tokens, reasoning_tokens, web_search_requests, token_budget, tokens_used}`, `tokens_used` the day's tokens with this message's charge and `token_budget` null for no budget.
- `outcome` is `ok`, `choice`, `depth_limit`, `time_limit`, `model_error`, `cut` or `cancelled`. A `cancelled` turn's client has gone, so it is recorded and logged but sent nothing.

### Tool loop

- Each model call streams; the tools it calls run in order and their answers go back in the next call. The turn ends when the model ends it, when it asks a choice, or at a limit:
  - at most 8 model calls a message (`MAX_MODEL_CALLS`), a call the provider paused and a failed call included;
  - 120 s a message (`TURN_LIMIT_MS`), under the 150 s wall clock of the Free plan and the 400 s of paid ones; each call is aborted when the message's time runs out;
  - at most 8,192 output tokens a call (`MAX_OUTPUT_TOKENS`).
- A call the provider paused, Anthropic's `pause_turn`, is sent again with its message last, which resumes it.
- A reply that stopped at the output limit ends the turn as `cut`, its tool calls not run.
- A client that goes away cancels the stream: nothing more is sent, the call in flight is read on to its end within the message's time, so that the usage its provider reports there is counted, no further call is made, and the turn is recorded as `cancelled` with what it used.
- A call that breaks off, fails or is cut is counted with the usage its provider had reported by then: Anthropic reports its input tokens when the message starts and its output as it goes, OpenRouter's responses and OpenAI's chat completions only at their end. A call that broke off or failed before any input was reported is counted an estimate of its input, the request's UTF-8 bytes over 4 (`BYTES_PER_TOKEN`); one the provider refused with an error status, none.
- A call that fails ends the turn. A network error, an abort, or a stream that breaks off or reports an error is `cancelled` when the client went away, `time_limit` when the message's time ran out, and otherwise `model_error`. Any other error is a defect: it is logged as `internal` and not recorded.
- A tool whose arguments are not JSON, or that refuses, answers the model with a sentence it can act on, marked as an error; a read PostgREST does not answer says to try again.

### Tools

- `list_decks`, `list_cards` and `search_cards` — `mcp`'s own, with its definitions, through the caller's token ([`mcp.md`](mcp.md) §Tools).
- `read_card_form` (`form`) — answers the form's guide as the caller is served it (§Card forms); a form that is none is refused naming the forms.
- `propose_deck` (`name`, `groups`) and `propose_cards` (`deck_id`, `groups`) — new cards, for a new note or one of the user's live notes: 1 to 20 groups, each `{title, format, cards}`, 100 cards at most over them, each card in `add_cards`' form. Each card is read as `add_cards` reads it; one whose card key matches a card of the note or an earlier card of the proposal is left out as a duplicate; a group with no card left is dropped. Over 100 cards is refused whole.
- `propose_changes` (`deck_id`, `groups`) — changes to up to 100 live cards of one note, in groups as above, each card in `update_cards`' form and read as it reads them.
- `regenerate_group` (`proposal_id`, `group_id`, `format`, `cards`) — remakes one group of a proposal of new cards that the conversation holds, or that this message showed, in the format, under the group's id and title; the proposal's other groups are kept as they were, and a card repeating one of theirs or the note's is left out.
- **One form a group** ([ADR 0197](adr/0197-make-the-card-forms-versioned-skills-an-index-the-assistant-always-sees-and-a-guide-per-form-it-loads-shared-with-mcp-and-hold-each-proposal-group-to-one-form.md)). Every card of a group takes the group's `format`, its form as `_shared/card_forms.ts` reads it from its blocks. A proposal tool given a card of another form shows nothing and answers a sentence naming each such card by its index and group, with the group's title and form and the card's form, and to move each into a group of its form.
- `read_study_record` (`deck_id?`, `period_days?`) — the caller's study record from `public.assistant_study_record` ([`server.md`](server.md) §Study record read), as the caller: each live deck's cards by progress (`new`, `learning`, `mastered`), its cards `due`, and its `answers`, `known` and `known_percent` within the last `period_days` (1 to 365, 30 by default, `DEFAULT_PERIOD_DAYS`, `MAX_PERIOD_DAYS`); and `most_missed`, up to 50 cards answered "Don't know" most often in it, each with its blocks as `list_cards` returns them, its deck, `missed` and `answers`. The answer is held to 60,000 characters (`READ_PAGE`): the least missed cards are left out, counted in `most_missed_cut`. It refuses a `deck_id` that is not a uuid or not a live deck of the user's, and a period out of bounds, with a sentence the model can act on. The tool reaches the model through its tool spec alone, not through the prompt, so no prompt version was added; `mcp` does not serve it.
- `ask_choice` (`prompt`, `options`) — sends a `choice` and ends the turn.
- `start_photo_job` (`instructions?`), `read_photo_job` (`job_id`, `from?`) and `cancel_photo_job` (`job_id`) — a photo job's start over the photos of the latest user turn that attached any, sending `job`; its status, counts and readings in order, at most 60,000 characters a page (`READ_PAGE`) and `next_from` for the rest; and its cancel (§Photo jobs). Each refuses with a sentence the model can act on: no photos attached, another job running, the day's tokens spent, photos not uploaded, or a job that is not the user's.
- The proposal tools write nothing. Each answers the model the proposal's and groups' ids and sizes, the cards left out and refused with their group and index, and that nothing is saved until the user adds it; a proposal of no card is refused with the reasons and sends nothing.

### Proposals

- A proposal is `{id, kind, deck: {id, name}, groups: [{id, title, format, cards: [{id, card}]}]}`, each id a version 7 uuid the function made:
  - `kind` `cards`, new cards, for a new note when `deck.id` is null; or `changes`, whose card ids are the cards' own;
  - `format` the card form every card of the group takes, `text`, `senses`, `cloze`, `table`, `image` or `mixed` (§Card forms);
  - `card` exactly what `add_cards` or `update_cards` takes, so a client draws it as `add_cards`' union.
- The server keeps no proposal: the client sends it back in the next turns and in the commit.

### Card forms

- The card forms are each 칸 type `add_cards` takes, `text`, `senses`, `cloze`, `table` and `image`, and `mixed` ([ADR 0197](adr/0197-make-the-card-forms-versioned-skills-an-index-the-assistant-always-sees-and-a-guide-per-form-it-loads-shared-with-mcp-and-hold-each-proposal-group-to-one-form.md)). A card's form is the one type it holds besides text: `text` when it holds text alone, and `mixed` when it holds two or more others; a kept sound accompanies as text does.
- Each form's skill, a one-line summary of when it fits and a guide with its rules, a good and a bad example and edge cases, is read through `card_form_skills()` with the caller's token, as `mcp` reads it: an admin is served a form's test version while one is set ([`server.md`](server.md) §Card-form skills). `_shared/card_forms.ts` keeps a caller's skills 60 s (`SKILL_CACHE_MS`), and an answer missing a form fails as Supabase not answering.
- The skills are read once a message, before it starts. The model is sent the configuration's prompt, then the index: what a card is and a card's form, each form with its summary, and that every card of a group takes the group's form. Neither the guides nor an instruction to read one are in it: that instruction is prompt v2's, so a plan's proposal turns spend a call on a guide, about one more full-context model call a proposal turn, only once an admin applies v2. The index is about 1,100 bytes, some 270 tokens, on every call.
- The working order is the prompt's, from prompt v2: understand the material and build what the user asks from it, not a copy of it; restate the requests and the plan; ask only what is unclear; build, reading each form's guide; revise one group on request ([ADR 0197](adr/0197-make-the-card-forms-versioned-skills-an-index-the-assistant-always-sees-and-a-guide-per-form-it-loads-shared-with-mcp-and-hold-each-proposal-group-to-one-form.md)). Prompt v2 is 스페셜's draft, served to admins, until an admin applies it; the active configurations send v1, and another plan takes v2 by a draft an admin saves in 말랑이.

### Commit

- The commit reads the proposal, and the cards whose ids `checked` names under their group, each group's at most once; a group or card the proposal lacks, or no card checked, is `400`.
- It writes them as the caller, through the shared write path and its refusals: a new note through `create_deck` and then `add_cards`; cards for a note through `add_cards`; changes through `update_cards`. A whole refusal is `422`; otherwise `200` with `deck` and the write tool's answer, its cards added, skipped and refused.
- A commit sent twice adds no duplicate to a note, by `add_cards`' duplicate rule, but makes a second new note.

### Photo jobs

- 말랑이 reads the chat's photos in a background job ([ADR 0198](adr/0198-read-the-chat-s-photos-in-a-background-job-on-supabase-queues-each-photo-a-step-of-the-assistant-s-model-charged-against-the-day-s-tokens.md)); the schema, queue and their functions are [`server.md`](server.md) §Photo jobs'.
- **The sweep.** A job whose chain broke while no client polls is resumed from the database: a `pg_cron` job requests the worker through pg_net each minute while a running job has a queued photo and has begun no read for 3 minutes, `STALE_MS`, once the owner has put the function's URL and the service-role key into Supabase Vault ([ADR 0203](adr/0203-resume-a-stalled-photo-job-from-the-server-with-a-pg-cron-sweep-that-requests-the-worker-through-pg-net-its-url-and-key-in-vault.md), [`server.md`](server.md) §Photo jobs).
- **Upload.** The client uploads each photo with the user's token to the private bucket `assistant-photos` at `{user id}/{photo id}`, a uuid it makes, JPEG, PNG or WebP of at most 6 MiB, before it sends the message naming them as `photos`.
- **Start.** `start_photo_job` makes the job's id, a version 7 uuid, and starts it through `start_assistant_job`, then asks for the worker (`POST /assistant/jobs/work` with the service-role key) and sends `job`. A job reads up to 50 photos (`MAX_JOB_PHOTOS`), with the user's instructions, at most 4,000 characters (`MAX_INSTRUCTIONS`); a user has one running job.
- **The worker** (`worker.ts`) answers 202 and runs in the background through `EdgeRuntime.waitUntil`: three lanes (`LANES`) take a photo each through `next_assistant_job_step` while 60 s (`STEP_LIMIT_MS`) of its 120 s (`WORK_LIMIT_MS`) remain, waiting 5 s (`IDLE_MS`) when every queued photo is hidden; when its time runs out it asks for a fresh invocation. One read is one streamed call of the job's configuration's provider, model and effort, with `READING_PROMPT`, a user turn of the photo's position and the job's instructions, the photo's Storage address signed for 600 s (`PHOTO_URL_SECONDS`), no tools and no web search, aborted at 60 s.
- A read is recorded through `finish_assistant_job_step` with its outcome, `ok`, `cut`, `model_error`, `time_limit` or `unreadable`, its tokens and its reading, at most 50,000 characters (`MAX_READING`): a reply read whole is `ok` and one stopped at the output cap `cut`, both kept; a photo Storage does not hold is `unreadable`, with no call; a network error, an abort or a stream that breaks off is `time_limit` past 60 s and otherwise `model_error`, as is a refused call, a missing key or Storage not answering. A failed read is charged as a failed message call is (§Tool loop), and retried by the queue.
- **The end.** Once a read leaves the job with no queued photo, or a cancel ends it, the worker or the cancel deletes the job's photos from the bucket through the Storage API; the readings stay with the job.
- **Poll.** `GET /assistant/jobs/{id}` answers `{id, status, photos: [{position, photo_id, status}], read, queued, failed, skipped, cancelled, created_at, finished_at}`, `status` `running`, `done` or `cancelled` and a photo's `queued`, `read`, `failed`, `skipped` (the day's tokens ran out) or `cancelled`; never a reading. A running job whose last read began more than 3 minutes ago (`STALE_MS`), or none since it started, asks for the worker again. `POST /assistant/jobs/{id}/cancel` answers `{id, status}`. Either answers `404` for a job that is not the caller's and `503` `unavailable` when Supabase did not answer.
- **Composing.** When the job is done, the client sends the next user turn, the user's own or one it writes, with the job on its assistant turn; the model reads the readings with `read_photo_job` and builds proposals with the proposal tools, from the whole conversation, so instructions given before and during the job both apply.
- **Clients** (#721, #722): the app's chat keeps the `job` event on the reply and follows the job ([`assistant-app.md`](assistant-app.md) §Photos and their job). Upload, send `photos`, keep `job` on the turn, poll every few seconds while it runs, offer cancel, and send a turn when it is done.

### Providers

- One adapter per provider in `providers.ts`, each streamed and read event by event; a turn with a photo sends its address beside its text as OpenRouter's `input_image`, OpenAI's `image_url` or Anthropic's image block with a `url` source, and a call of no tools sends OpenAI no `tools` field; a read that stops before the body ends, at `[DONE]`, an error or a break, cancels the body, closing the connection:
  - **OpenRouter** — its Responses API (`/api/v1/responses`), stateless, with the prompt as `instructions`, the tools as functions, `reasoning.effort` the configuration's, `none` included, and with web search on, the `openrouter:web_search` server tool on the Exa engine with `max_uses` ([ADR 0190](adr/0190-serve-the-assistant-from-an-edge-function-that-streams-a-tool-loop-proposes-cards-in-groups-and-commits-what-the-user-checks-under-a-per-plan-daily-limit.md) records why not chat completions). Citations come from `url_citation` annotations. Only a `function_call` item is a call the function runs; a server tool's item, such as `openrouter:web_search`, is not. Every output item, those included, is sent back in the next call.
  - **OpenAI** — chat completions with the tools as functions and `reasoning_effort` unless it is `none`; it has no native search, so a configuration on it searches nothing.
  - **Anthropic** — messages with the tools, version `2026-10-21`, thinking adaptive with `output_config.effort`, or off at `none` as Anthropic's per-model table turns it off: `between_tools` on Claude Sonnet 5.5, `disabled` on the others. With web search on, it sends `web_search_20250305` and `web_fetch_20250910`, the basic variants every current model takes, each with `max_uses`. Web fetch also takes `max_content_tokens` 20,000 (`MAX_FETCH_TOKENS`) and fetches no URL found only in a function tool's answer (`url_sources`). Citations come from `citations_delta`; every block of a call, thinking with its signature, is sent back as it came.
- **Searches a turn.** The configuration's searches are a message's, shared by its calls and by Anthropic's web fetches: each call is offered those the earlier calls left, as each search tool's `max_uses`, and none once they are spent. One call may use what is left on each of Anthropic's two tools.
- Usage per call: input and output tokens; reasoning tokens, which the output tokens include, from OpenRouter's `output_tokens_details.reasoning_tokens`, OpenAI's `completion_tokens_details.reasoning_tokens` or Anthropic's `output_tokens_details.thinking_tokens`; searches from OpenRouter's `server_tool_use_details.web_search_requests` or Anthropic's `server_tool_use.web_search_requests`. Anthropic's web fetches, which cost only tokens, count against the searches a turn but are not recorded. A message's usage is the sum.

### Configuration and budget

- A configuration of an Anthropic model that cannot run at its effort by the per-model table is refused when saved: `none` on a model whose thinking is always on, or another effort on one with extended thinking alone ([`server.md`](server.md) §Assistant).
- The provider, model, prompt, web search, searches a turn and reasoning effort are the caller's plan's assistant configuration's, read at each message through `begin_assistant_message`: an admin, on 스페셜, is served 스페셜's draft while one is set ([`server.md`](server.md) §Assistant). Keys are Vault's, read through `_shared/keys.ts` and kept 60 s.
- The seed serves each plan on its photo configuration's provider and model, OpenRouter's `anthropic/claude-haiku-5.5` in production by ADR 0182's context, with no reasoning, or effort `low` on a model whose thinking is always on, 3 searches a turn, and web search off for Free and on for Pro, Max and 스페셜, the PM's default the owner may change.
- **The budget** ([ADR 0195](adr/0195-meter-the-assistant-by-a-daily-token-budget-per-plan-charged-when-a-message-ends-shorten-a-resent-reply-and-save-a-draft-after-a-check-call.md), superseding ADR 0190's daily message limit). Each plan has a daily token budget in Asia/Seoul, approved by the owner on 2026-11-05 as Free 200,000, Pro 2,000,000, Max 6,000,000 and 스페셜 none.
  - A message starts, before any model call, only when its provider has a key, the day's tokens charged are under the budget, and no other message of the user is running; it is refused `rate_limited` or `busy` otherwise.
  - It is charged when it ends, through `finish_assistant_message`, before its `usage` event: its input and output tokens summed over its calls, the output including the reasoning tokens, not weighted by price. The message that crosses the budget is charged whole: at most 8 calls, each at most 8,192 output tokens over an input the model's context window bounds.
  - A client refused `busy` sends the message again after a few seconds; a message its client cancelled stays running until its call ends and is recorded.
  - The check and the charge run under the user's lock ([`server.md`](server.md) §Assistant). A failed record leaves the answer standing, the message uncharged, and the log says so.
  - Web searches are not charged against the budget; a turn's searches stay capped by its configuration.

### Draft

- `POST /functions/v1/assistant/settings/configuration` with `{plan, provider, model, prompt_version_id?, web_search, max_searches, reasoning_effort}` saves an admin's draft of a plan's assistant configuration, as extract-cards' `settings/configuration` saves a photo draft ([`ai-extraction.md`](ai-extraction.md), [ADR 0195](adr/0195-meter-the-assistant-by-a-daily-token-budget-per-plan-charged-when-a-message-ends-shorten-a-resent-reply-and-save-a-draft-after-a-check-call.md)):
  - the caller is authenticated and must be an admin, as `admin_ai_session` answers it; no recent sign-in is asked;
  - the body names a plan, a provider, a model in its provider's form, web search, 1 to 10 searches a turn and an effort; a prompt version is optional, the draft keeping the one it had, or else the active one's;
  - a model that cannot run at the effort by Anthropic's per-model table is refused before any call, as the database asks it through `assistant_effort_fits` ([`server.md`](server.md) §Assistant);
  - one call with the provider's key in Vault, the model, the effort, the tools and web search as the draft has them, through the provider's adapter, read to its end, at most 30 s (`CHECK_TIMEOUT_MS`); only when it answered is the draft saved, through `save_assistant_configuration`.
- It answers `200` `{saved: true, configuration_id}`, or `{error}`: `400` `bad_request`, also when the database refuses the draft; `400` `effort_unsupported`; `401` `unauthenticated`; `403` `forbidden`; `409` `no_key`; `422` `key_refused`, `model_not_found` or `call_failed` when the check call failed; `503` `unavailable` when Supabase did not answer.
- An admin reads each plan's configuration and budget, saves a draft through this route and a prompt, and applies or ends a draft on admin's 말랑이 ([`web-admin.md`](web-admin.md) §Area).

### Log and privacy

- The conversation is not stored: the server keeps a message's record and usage, never its text, a card or a reply. A photo job keeps the user's instructions and each photo's reading until it is purged 7 days after it began, and its photos until it ends (§Photo jobs).
- Each request logs one JSON line, and each photo read one of route `work`: `route` (`message`, `commit`, `settings`, `job`, `cancel` or `work`), `user_id`, `plan`, `provider`, `model`, `model_calls`, `input_tokens`, `output_tokens`, `reasoning_tokens`, `web_search_requests`, `latency_ms`, `outcome_recorded` and `outcome`, each null where it does not apply; never the token, a key, a message or a card. A stream logs its line when it ends.

- [ADR 0197](adr/0197-make-the-card-forms-versioned-skills-an-index-the-assistant-always-sees-and-a-guide-per-form-it-loads-shared-with-mcp-and-hold-each-proposal-group-to-one-form.md) records the card forms as versioned skills shared with MCP, why the index is in the prompt and a guide loaded, why a text block takes the form of what it accompanies, one form a group superseding ADR 0190's group format, and the working order; issue #751 records the owner's and the PM's decisions.
- [ADR 0198](adr/0198-read-the-chat-s-photos-in-a-background-job-on-supabase-queues-each-photo-a-step-of-the-assistant-s-model-charged-against-the-day-s-tokens.md) records the photo jobs: why a pgmq queue and not a table or a separate function, the platform limits the worker keeps under, why a photo is sent by address, why a photo is read whole and the instructions applied when composing, the steps three at a time apart from messages, and what is stored for 7 days; issue #750 records the owner's and the PM's decisions.

## Open questions

- Whether the PM's defaults hold once the owner prices them: web search on for paid plans, no reasoning, Haiku 5.5 for every plan (#713's PR).
- Whether tokens should be weighted by price once a plan's spend shows plain tokens do not track it.
- The admin pages for the card-form skills are #751's next pull request.
- The study day's time zone in `read_study_record` defaults to Asia/Seoul until the clients send theirs (§Tools).
- A photo attached in the chat is read by a photo job (§Photo jobs), not through `extract-cards`.
- Whether to cap a job below 50 photos, or a photo's reading below 8,192 output tokens, once its cost against Free's budget is seen (#750's pull request proposes the caps to the owner).
- Photos uploaded and never named by a job stay in the bucket until the account is deleted.
- OpenRouter's Responses `input_image` with an https address is not checked against OpenRouter's schema text.
