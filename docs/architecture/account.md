# Account

The `account` domain: signing in with Google, and with Apple on iOS, through Supabase Auth, the session it starts, deleting the account, and the configuration it reads.

## Current decisions

### Surface and location

- The domain lives in `app/lib/account/`; its public surface is `app/lib/account/account.dart`, with internals under `app/lib/account/src/` ([ADR 0002](adr/0002-domain-public-surface-and-shared-database.md)).
- The surface exports:
  - `connectAccount`, which returns an `AccountConnection`: the service, and the `SupabaseClient` it signs in through, null when the configuration cannot sign anyone in; and `accountDefines`;
  - `AccountService`, which signs in with Google, Apple or an email code, signs out and deletes the account, and `accountServiceProvider`, which the composition site overrides;
  - the state: `AccountState`, `SignedOut`, `SignedIn` with the account's `UserId`, `AccountUnavailable`;
  - `AccountData`, `AccountDataNotCleared` and `accountDataProvider`, the device's data that sign-out pushes and clears, which the composition site overrides with the `sync` domain's, so this domain does not depend on it, a seam that breaks a behavioural cycle ([`sync.md`](sync.md));
  - the failures: `AccountFailure`, `AccountOffline`, `AccountMisconfigured`, `AccountRejected`, `AccountSuspended`, `AccountRateLimited`, `AccountCodeRefused`, `AccountAddressRefused`;
  - `AccountGate`, the app's home, which takes the app it opens while signed in as a constructor argument: the composition site passes `home/`'s `HomeScreen`, so this domain depends on no other ([ADR 0017](adr/0017-require-sign-in-through-an-account-gate.md), [ADR 0039](adr/0039-name-every-top-level-folder-by-its-responsibility-compose-across-domains-in-a-home-shell-and-keep-seams-off-screens.md));
  - `AccountScreen`, the settings screen, which takes the sync status and the study settings' rows it shows as constructor arguments;
  - `ProfileButton`, the signed-in account's email's first character, upper-cased, in Pretendard, in a round button 44 across over its edge, a person's outline for an account with no email, named "설정", which calls the callback its caller gives; on the hero it takes `heroButton` under `onHeroButton`, elsewhere the raised surface under `accent`;
  - `appVersionProvider`, the version the settings screen names, which the composition site overrides;
  - the plan: `PlanServer`, which reads the account's plan from the server, with `SupabasePlanServer` over `public.my_plan()` ([`server.md`](server.md) §Store plans) and `UnavailablePlanServer`, and `planServerProvider`; `PurchaseStore`, the app's own interface over the store's purchases, with `connectPurchases`, which returns the RevenueCat-backed one or `UnavailablePurchaseStore`, and `purchaseStoreProvider`; and `purchaseOfferProvider`, the function that opens the purchase sheet, null unless the account may buy. The composition site overrides the two providers, and hands `photo_import` the offer through its own `photoLimitOfferProvider`, so neither domain imports the other.
- It is the only domain that imports `google_sign_in` ([ADR 0006](adr/0006-account-native-google-sign-in.md)) and `sign_in_with_apple` ([ADR 0186](adr/0186-sign-in-with-apple-on-ios-through-the-system-sheet-and-supabase-with-apple-s-button-under-google-s.md)). `sync` and `sharing` also import `supabase_flutter`, for PostgREST with the client `connectAccount` returns ([ADR 0015](adr/0015-sync-protocol-and-conflict-policy.md), [ADR 0020](adr/0020-public-decks-in-a-sharing-domain.md)). It is also the only domain that imports `purchases_flutter`, pinned in `app/pubspec.yaml`, in `app/lib/account/src/revenuecat_store.dart` alone; every other file, and every test, uses `PurchaseStore`.
- `home/`'s 홈 holds `ProfileButton` at the right of its top bar, which opens `AccountScreen` over the menu ([ADR 0165](adr/0165-open-on-today-over-the-last-seven-days-move-the-notes-to-a-tab-and-open-settings-from-the-profile-button.md)), with `sync`'s `SyncStatusView`, and `study`'s `DailyMinutesRow`, `study`'s `AutoplayAudioRow` and `deck`'s `PartOfSpeechPresetsRow`, in that order, as its study settings' rows ([`home.md`](home.md)).

- The gate shows the state the service holds now and never waits on the network: a session restored at start opens the app offline, expired or not, while its refresh runs in the background.
- When the state leaves `SignedIn`, by sign-out or by the client dropping the session, the gate closes every screen opened over the app, so the sign-in screen is the only one left.

### Sign-in and session

- Google sign-in opens the platform's Google account picker (`GoogleSignIn.authenticate`), then passes the Google ID token and an access token for `email` and `profile` to Supabase's `signInWithIdToken`.
- Apple sign-in, on iOS, opens the system's Apple ID sheet (`SignInWithApple.getAppleIDCredential`) for the email and the full name, then passes the identity token to `signInWithIdToken` with the Apple provider. Each sign-in draws its own nonce: Apple receives its SHA-256 as hex, and Supabase the raw value ([ADR 0186](adr/0186-sign-in-with-apple-on-ios-through-the-system-sheet-and-supabase-with-apple-s-button-under-google-s.md)).
- Apple shares the name on an account's first sign-in alone; when it does, the service stores `full_name`, the given and family names joined by a space, with `given_name` and `family_name` in the user's metadata through `updateUser`. A failure there is reported through `FlutterError.reportError`, and the user stays signed in.
- Email sign-in has two steps on `EmailSignInScreen`, opened over the sign-in screen and titled "이메일로 계속하기" ([ADR 0214](adr/0214-sign-in-with-an-email-code-on-the-phone-in-a-screen-opened-over-the-sign-in-screen-with-three-failures-added-to-the-account-failures.md)):
  - The address step, "이메일" hinted "name@example.com", takes an address and checks its shape before it sends: "이메일 주소를 확인해 주세요." under the field otherwise. "코드 받기" calls `AccountService.sendEmailCode`, which calls `signInWithOtp(email:, shouldCreateUser: true)`; Supabase creates the account on first use.
  - The code step names the address ("…로 보낸 6자리 코드를 입력해 주세요.") and takes the code in a field "6자리 코드" with the number keyboard, `AutofillHints.oneTimeCode` and a filter that keeps only digits, up to 128, the most `review-sign-in` takes (so a pasted "123 456" or "코드 123456" is the code). It calls `verifyEmailCode` on "로그인", which is disabled below six digits, or at once when the digits arrive whole into an empty field (pasted or filled by the platform). A code typed key by key waits for the button, since its first six digits may be the start of a review code ([ADR 0228](adr/0228-choose-app-review-s-sign-in-by-the-code-s-digit-count-keep-the-code-field-to-digits-and-sign-in-on-a-code-that-arrives-whole.md)). The session that answers is the state `SignedIn`; the screen closes and the gate shows the app.
  - `verifyEmailCode` keeps the digits of the code and chooses the path by their count: under 12, they go to `verifyOTP(email:, token:, type: OtpType.email)`; 12 or more go to App Review's path below, so a pasted sentence holding a code is still its digits. A real code has six digits and the owner's review code at least 12, digits only, 16 recommended ([ADR 0226](adr/0226-sign-one-app-review-address-in-through-the-review-sign-in-function-with-a-fixed-code-kept-in-vault-and-hand-the-app-the-token-hash-of-an-email-sign-in.md)), so no code of either kind takes the other's path.
  - "N초 뒤에 코드를 다시 받을 수 있어요" counts down from 60 seconds, the interval the project sets between codes, then "코드 다시 받기" sends again to the same address; a rate-limit refusal that names its wait restarts the count from it. "이메일 주소 바꾸기", the back arrow and the system's back return to the address step, which keeps the address typed; back from the address step leaves the screen.
  - A failure is shown under the field it concerns, as its message, and the step stays.
  - The code's email, its 10-minute life and the limits on resends are the server's: [`server.md`](server.md) §Auth settings ([ADR 0213](adr/0213-sign-in-by-email-with-a-six-digit-code-sent-in-korean-and-set-the-production-project-s-auth-by-hand-since-its-config-toml-section-is-not-applied.md)).
- **App Review's sign-in** ([ADR 0226](adr/0226-sign-one-app-review-address-in-through-the-review-sign-in-function-with-a-fixed-code-kept-in-vault-and-hand-the-app-the-token-hash-of-an-email-sign-in.md)): one address the owner sets signs in with one fixed code, also the owner's, both in Vault, so a reviewer needs no mailbox. The phone sends `{email, code}` to the `review-sign-in` function, which answers `{token_hash, type: "email"}` for that pair and `401` for anything else, and the phone turns the hash into the session with `verifyOTP(tokenHash:, type: OtpType.email)`; the account is an ordinary 무료 account created on first use. The owner's review code is digits only, at least 12 (16 recommended, for example `LC_ALL=C tr -dc 0-9 </dev/urandom | head -c 16`), which [ADR 0228](adr/0228-choose-app-review-s-sign-in-by-the-code-s-digit-count-keep-the-code-field-to-digits-and-sign-in-on-a-code-that-arrives-whole.md) takes in place of ADR 0226's hex example. The phone types nothing new for it: the reviewer enters the review address and the fixed code on the email screen's two steps (the address step still sends that address a real email code), and the phone holds neither. A `401` from the function is `AccountCodeRefused`, a `429` is `AccountRateLimited` with a wait of 10 minutes (the function's `Retry-After`, which the Edge Functions client's exception does not carry, so the phone holds the figure), a request that never arrived or a `5xx` is `AccountOffline`, an answer without a token hash or any other status is `AccountRejected`, and a refusal of the hash by `verifyOTP` is mapped as an email code's is. The contract, the limits and the owner's steps are in [`server.md`](server.md) §Review sign-in.
- Supabase links a sign-in to the account that holds its verified email, so Apple and Google with the same address reach one account; an address from Apple's "Hide My Email" relay is its own, so it starts another.
- Each run draws one random nonce for Google when it initializes Google Sign-In: Google receives its SHA-256 as hex and puts it in the ID token, and `signInWithIdToken` receives the raw value, which Supabase checks against the token. Every sign-in in a run carries the same nonce, since Google Sign-In is initialized once per run ([ADR 0008](adr/0008-google-sign-in-nonce.md)).
- `supabase_flutter` stores the session on the device and restores it at start; the app then opens past the gate.
- Sign-out first asks `AccountData` to push every unsynced change. When some did not arrive, a confirmation sheet, "동기화하지 않고 로그아웃할까요?", offers "취소", which keeps the account signed in, and "그래도 로그아웃".
- It then ends the Supabase session on the device, tells the server, and signs out of Google so the next sign-in shows the picker again. Once the device is signed out, even after a failure telling the server, `AccountData` clears the device's data; a failure there is shown in a snack bar.
- The state is `SignedOut`, `SignedIn` with the account's email, or `AccountUnavailable` when the build's configuration cannot sign anyone in.

### Deletion

- "계정 삭제" asks first through `showAppConfirm`: "계정을 삭제할까요?", one sentence saying the decks, cards and study history go from the server and this device while decks others copied and the Google account stay, then "취소" and, last, a red "삭제" ([ADR 0026](adr/0026-delete-the-account-through-an-edge-function.md)).
- `AccountService.deleteAccount` posts to the `delete-account` Edge Function through the Supabase client's Edge Functions client, which sends the session's access token; the request names no user. For an account with an Apple identity the request carries `{"apple_authorization_code": ...}`, the code of a fresh Apple sheet, shown after the confirmation with no scopes, read from the session user's identities (a provider `apple` among them, a session that lists none holding none), and sent at once and never kept; cancelling that sheet cancels the deletion: `deleteAccount` returns false, nothing is deleted, and the screen neither signs out nor clears the device's data nor shows a message; any other failure of the sheet is an `AccountRejected`. A Google or email account shows no sheet and sends no body ([ADR 0210](adr/0210-revoke-the-apple-authorization-when-an-account-is-deleted-by-exchanging-a-fresh-authorization-code-at-deletion-and-never-let-a-failed-revocation-stop-the-deletion.md), #731), and a request without a code deletes as before. The function first deletes the user's media files from the `media` bucket and the photos it sent 말랑이 from the `assistant-photos` bucket through the Storage API, then, for an Apple account sent a code, revokes its Apple authorization, then deletes the token's user, and the server's cascade deletes every row it owns ([`server.md`](server.md), [ADR 0107](adr/0107-store-media-in-a-private-supabase-storage-bucket-named-by-media-id-and-give-each-deck-an-image.md)).
- Once the account is deleted, the screen signs out of Supabase and Google and clears the device's data through `AccountData`, as sign-out does but without pushing first. The gate then shows the sign-in screen.
- **Apple revocation.** The function exchanges the code at Apple's `/auth/token` for a refresh token and revokes it at `/auth/revoke`, signing the client secret with the owner's Sign in with Apple key from the function secrets `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_CLIENT_ID` (the app's App ID, `app.knowno`) and `APPLE_PRIVATE_KEY` (the `.p8` file's text). Nothing Apple does or the project lacks stops the deletion: a refusal, no answer, a code of another Apple account, no code, or a missing secret leaves the account deleted, 204, with the outcome in the function's log as `apple`. No Apple token is stored.
- A failed deletion changes nothing: the account stays signed in with its data.
- Merging the pull request that changes the function deploys it ([`server.md`](server.md) §Edge Function deploys); it lives in `supabase/functions/delete-account/` with its Deno tests, run by `make test` through `scripts/deno.ts` with Supabase Auth replaced by a fake `fetch`.

### Configuration

- `app/config/dev.json` holds the Supabase URL, `https://api.knowno.app`, the project's custom domain, the Supabase publishable key, the Google web client ID (passed as the server client ID) and the iOS client ID. The values are public. The Android client is matched by package name, `app.knowno`, and signing certificate, so no Android client ID is configured ([ADR 0134](adr/0134-name-the-app-knowno-serve-it-at-knowno-app-identify-it-as-app-knowno-and-reach-the-backend-at-api-knowno-app.md)).
- The iOS client is the one created for `sh.garam.smartman`, its bundle ID changed by the owner to `app.knowno`, so the old app's install can no longer sign in with Google.
- `make test`, `make build` and the README's `flutter run` pass the file with `--dart-define-from-file`; no Dart source holds a value.
- `app/config/dev.json` also holds `REVENUECAT_APPLE_API_KEY` and `REVENUECAT_GOOGLE_API_KEY`, RevenueCat's public SDK keys for iOS and Android, both empty until the PM creates the RevenueCat project. `connectPurchases` reads the one for the platform; an empty key, or a platform with neither, gives `UnavailablePurchaseStore`: the app builds and runs, and the purchase sheet says purchases are not ready yet. Nothing makes a missing key `AccountUnavailable`.
- `purchases_flutter` is configured when the account becomes signed in, with the Supabase user id as the app user id, and logged out at sign-out, so the customer RevenueCat sees is the one `my_plan()` reads ([`server.md`](server.md) §Store plans).
- The values are parsed once at start. A missing or malformed value, or a key that is not a publishable key, makes the state `AccountUnavailable`, with the reasons in its `AccountMisconfigured`; the gate then shows the message and no app.
- The terms of service and the privacy policy are the web's pages, `https://knowno.app/terms` and `https://knowno.app/privacy` ([`web-legal.md`](web-legal.md)), constants in `app/lib/account/src/legal.dart` that no configuration changes. Each link opens its page in the platform's browser through `url_launcher`, with a snack bar when it does not open ([ADR 0032](adr/0032-publish-the-legal-documents-on-the-web-and-link-both-clients-to-them.md)).
- The app's version comes from the platform through `package_info_plus`, read once before the first frame.
- `app/ios/Runner/Info.plist` holds the reversed iOS client ID as a URL scheme. `scripts/check-ios-client-id.ts`, run by `make lint`, fails when it differs from `app/config/dev.json`.
- `app/ios/Runner/Info.plist` sets `ITSAppUsesNonExemptEncryption` to `false`: the app's only encryption is the operating system's TLS, so App Store Connect does not ask the export-compliance question at each upload ([#725](https://github.com/garamsh/knowno/issues/725)).
- `scripts/check-secrets.ts`, run by `make lint`, fails when any file the repository tracks or would track holds a Supabase secret key or service-role key.
- The Swift packages `google_sign_in_ios` brings are pinned in the committed `Package.resolved` files under `app/ios/` ([ADR 0006](adr/0006-account-native-google-sign-in.md)).
  - `.github/dependabot.yml` has no `swift` entry for them. Dependabot's `swift` updater reads an Xcode project's `Package.resolved` (`swift/lib/dependabot/swift/file_fetcher.rb` in dependabot-core at `3ac9b7af9e729e80c8d1ddfbf6ae3839675fa77e`). It takes the requirements from the `XCRemoteSwiftPackageReference` entries of `project.pbxproj` (`file_parser/pbxproj_parser.rb`, same revision), and `app/ios/Runner.xcodeproj/project.pbxproj` has none: it names only `FlutterGeneratedPluginSwiftPackage` under `app/ios/Flutter/ephemeral/`, which git ignores. Without those requirements, Dependabot would move the pins past what `google_sign_in_ios` accepts.
  - The mover is the PM. To re-resolve within the current requirements: delete both `Package.resolved` files, then in `app/` run `flutter build ios --config-only --no-codesign --dart-define-from-file=config/dev.json`, which rewrites the copy under `Runner.xcodeproj/`, and `xcodebuild -resolvePackageDependencies -workspace ios/Runner.xcworkspace -scheme Runner`, which rewrites the one under `Runner.xcworkspace/`. Commit both.
- Only the `dev` environment exists; flavors wait for M7 ([ADR 0006](adr/0006-account-native-google-sign-in.md)).

### Failures

- Cancelling Google's picker or Apple's sheet is not a failure: sign-in returns and nothing is shown.
- Each expected failure is an `AccountFailure`:
  - `AccountOffline` — Supabase could not be reached, or answered with a server error;
  - `AccountMisconfigured` — the configuration is missing or malformed, Google reports a client or provider configuration error, the device has no Apple ID sheet, or Supabase has the provider disabled or signups off (`provider_disabled`, `email_provider_disabled`, `signup_disabled`);
  - `AccountRejected` — Google, Apple or Supabase refused, the ID token included, or the provider returned no ID token;
  - `AccountRateLimited` — Supabase Auth refused a request for coming too often (`over_email_send_rate_limit`, `over_request_rate_limit` or a 429), or `review-sign-in` did (a 429, with a wait of 10 minutes), with `retryAfter` from the "N seconds" its message names, null where it names none;
  - `AccountCodeRefused` — the email code was refused (`otp_expired`), or `review-sign-in` refused the pair (a 401); Auth answers a wrong code and an expired one alike, so they are one failure whose message names both;
  - `AccountAddressRefused` — Auth would not send to the address (`validation_failed`, `email_address_invalid`, `email_address_not_authorized`);
  - `AccountSuspended` — Supabase Auth answered `user_banned`, since an admin suspended the account; its message says so and where to write ([ADR 0072](adr/0072-suspend-a-user-through-supabase-auth-s-ban-and-restrictive-write-policies-remove-a-public-deck-from-sharing-for-good-and-read-any-deck-in-the-admin-area.md)).
- A deletion that never reached the function, or that it answered with a 5xx, is `AccountOffline`; any other refusal, or a success other than 204, is `AccountRejected`.
- The sign-in screen shows a failure from sign-in, and the email screen one from its two steps under the field, the settings screen one from sign-out or deletion, in a snack bar, as a localized message; a rejected deletion says the account could not be deleted. Any other error propagates.
- A background refresh that cannot reach Supabase is left to the client, which keeps the session and retries; any other refresh error goes to `FlutterError.reportError`.
