# Web

The web app in `web/`: its stack, the rules that keep it portable between Vercel and a container, when Vercel builds it, its image, the session and the proxy, the shell and its pages' common parts, the server reads every feature makes, the theme and the user's choice of it, and its checks. Each feature has its own document ([ADR 0081](adr/0081-document-each-web-feature-in-its-own-responsibility-document-beside-web-md-and-name-each-test-file-s-behaviour-in-one-line.md)): [`web-account.md`](web-account.md), [`web-decks.md`](web-decks.md), [`web-study.md`](web-study.md), [`web-admin.md`](web-admin.md) and [`web-legal.md`](web-legal.md).

## Current decisions

### Project

- `web/` is a Next.js 16.4.1 App Router project of its own, with strict TypeScript and the `src/` layout of stack-nextjs.md §1 ([ADR 0019](adr/0019-web-app-stack-portability-and-sign-in.md)). It runs on Node.js 24.22.0, named once in `web/.nvmrc`.
- Its packages are pinned exactly in `web/package.json` and locked in `web/package-lock.json`. Dependabot's `npm` entry for `/web` proposes their moves, except TypeScript 6.1 and later, ESLint 10 and later, and `@types/node` 25 and later:
  - typescript-eslint 8.71.2 accepts TypeScript below 6.1;
  - eslint-config-next 16.4.1 brings React, import and jsx-a11y lint plugins that accept ESLint 9 at most;
  - `@types/node` follows `web/.nvmrc`, which the PM moves with the Dockerfile's base image.
- `npm audit --package-lock-only` in `web/` reports five high findings, all from one advisory, [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), published 2026-09-18: `braces` 3.0.3 and earlier overflow the stack on deeply nested patterns. It has no patched version (`gh api /advisories/GHSA-vfj7-8cjw-p6xm` gives `first_patched_version` null), so no exact upgrade or `overrides` entry removes it; Dependabot's `npm` entry for `/web` moves it once `braces` or the plugin ships a fix. Its one path is eslint-config-next 16.4.1, `@next/eslint-plugin-next` 16.4.1, `fast-glob` 3.3.1, `micromatch` 4.0.8, `braces` 3.0.3. It is not reachable:
  - it is a lint-time dependency only: `npm ls --omit=dev braces` is empty, so it is outside the production tree, and the image's runtime stage takes only the standalone server, the static files and `public/` from the build stage;
  - the plugin calls `fast-glob` only from `no-html-link-for-pages`, through `dist/utils/get-root-dirs.js` in `@next/eslint-plugin-next` 16.4.1, and only when `settings.next.rootDir` is set. `web/eslint.config.mjs` sets no `settings`, so `braces` never parses a pattern.
- `web/src/` holds the closed list of top-level folders [`structure.md`](structure.md) names ([ADR 0039](adr/0039-name-every-top-level-folder-by-its-responsibility-compose-across-domains-in-a-home-shell-and-keep-seams-off-screens.md)): the routes in `app/`, with the legal documents in a `(legal)` route group; the features `account`, `admin`, `decks`, `study` and `legal` under `features/`; the foundations `design/`, whose components and helpers [`structure.md`](structure.md) lists, and `supabase/` (the Supabase adapter); `styles/`, `testing/` and `__tests__/`; and `env.ts` and `proxy.ts`.
- Every user-facing string is Korean, in 해요체, written where it is rendered; the root layout declares `lang="ko"`.
- Icons are `lucide-react`'s, pinned exactly like every package ([ADR 0027](adr/0027-draw-both-clients-in-the-smartman-brand-and-the-v2-screens.md)).

### Portability

- No Vercel-only feature: no `@vercel/` package and no `runtime = 'edge'` anywhere under `web/`. `make lint` fails on either through `scripts/web.ts`, after checking that its pattern still finds both in two control lines.
- The build is `output: "standalone"`, and runs on the Node.js runtime.
- On Vercel the web's address is `https://knowno.app`, and `www.knowno.app` redirects to it; the admin area's is `https://admin.knowno.app`, the same deployment, which the proxy routes by host ([ADR 0178](adr/0178-serve-the-admin-area-at-admin-knowno-app-from-the-same-web-app-routed-by-host-in-its-own-shell-and-session.md)); production's `NEXT_PUBLIC_SUPABASE_URL` is `https://api.knowno.app` ([ADR 0134](adr/0134-name-the-app-knowno-serve-it-at-knowno-app-identify-it-as-app-knowno-and-reach-the-backend-at-api-knowno-app.md)). The domains, that variable and `KNOWNO_SERVICE_ORIGIN` (below) are the owner's to set.
- On Vercel the functions run in `hnd1` (Tokyo, AWS `ap-northeast-1`), the Supabase project's region, so each request a page makes to Supabase stays within one region ([ADR 0030](adr/0030-read-only-what-each-web-page-shows-and-size-the-web-from-the-app-tokens.md)). `web/vercel.json` declares it, as `regions`, and holds nothing else but the Ignored Build Step of §Deploy ([ADR 0180](adr/0180-skip-vercel-s-build-when-none-of-the-web-build-s-inputs-changed-since-the-branch-s-last-deployment.md)), which decides whether Vercel builds and changes nothing the app does: a container never reads the file, and a key that changed behaviour, a rewrite or a header, would make Vercel and the container differ. Vercel reads the file from the project's Root Directory, `web`, and it overrides the region set in the project's settings. Vercel's function-region documentation (updated 2026-08-11) deploys Routing Middleware to every region whatever this setting says; `proxy.ts` makes no request to Supabase while the signing key is cached in the process and the session's access token is fresh, so where it runs adds no request to a page. A container runs where it is deployed, and its operator places it near the Supabase project.
- The configuration is environment variables, parsed once by `web/src/env.ts`: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. A missing or malformed value, or a key that is not a publishable key, fails the build. All are public, and no secret is read: the app uses the publishable key and the user's session.
- They are frozen into the build, so a build, and an image, belongs to one Supabase project. `scripts/web.ts` builds with the values of `app/config/dev.json` unless the environment already sets them.
- One more variable is read as the server runs, not from the build: `KNOWNO_SERVICE_ORIGIN`, the service's origin and nothing more, `https://knowno.app` on Vercel and `http://localhost:3000` on a machine (`web/.env.example`), whose admin host is the same origin with `admin.` before its name ([ADR 0178](adr/0178-serve-the-admin-area-at-admin-knowno-app-from-the-same-web-app-routed-by-host-in-its-own-shell-and-session.md)). Without the `NEXT_PUBLIC_` prefix Next.js leaves it on the server and does not inline it (Next.js 16.4.1, `environment-variables.md` §Runtime Environment Variables), so one image serves wherever its operator sets it, with `--env`. `web/src/env.ts` parses it at the proxy's first request and keeps it; a missing value, or one that is not an http(s) origin alone, fails every request the proxy runs on. On Vercel it is set for Production and Preview in the project's settings, and a change reaches only the next deployment (Vercel's "Environment variables", updated 2026-09-17).
- `GET /api/health` answers `{"status":"ok"}` with 200 and reads nothing.
- `next.config.ts` traces the engine's `.wasm` into the `/record` route's output with `outputFileTracingIncludes`, a Next.js option and no Vercel-only feature, so the standalone server and each serverless function carry the file the server reads ([ADR 0047](adr/0047-read-the-web-record-through-two-server-functions-and-fold-it-through-the-engine-on-the-server.md)).

### Deploy

- Vercel builds the web only when something its build reads has changed since the branch's last successful deployment ([ADR 0180](adr/0180-skip-vercel-s-build-when-none-of-the-web-build-s-inputs-changed-since-the-branch-s-last-deployment.md)). `web/vercel.json`'s `ignoreCommand` is `git diff --quiet "$VERCEL_GIT_PREVIOUS_SHA" HEAD --` over the inputs below, then `|| false`. Vercel runs it from the Root Directory, `web`, cancels the build where it exits 0 and builds where it exits 1 (Vercel's [project settings](https://vercel.com/docs/project-configuration/project-settings#ignored-build-step), updated 2026-09-21, read 2026-11-04). Its [Ignored Build Step guide](https://vercel.com/kb/guide/how-do-i-use-the-ignored-build-step-field-on-vercel), updated 2026-10-16 and read the same day, says any exit of 1 or more builds, but git's 128 for a commit it cannot read marked this branch's first preview `Error` (`dpl_HNVre9238uekJjTLfMTgZYBHVxKM`, 2026-11-04), so `|| false` turns every git failure into 1.
- The inputs, found from the build:
  - `web/`, the project itself.
  - `app/assets/fonts/`: `web/src/styles/fonts` links to it, the root layout's `next/font/local` reads the fonts through the link, and `next.config.ts` names it in `turbopackAdditionalRoots`.
  - `engine-wasm/pkg/`: `web/src/features/study/engine-wasm` links to it, the study feature imports the module through the link, `outputFileTracingIncludes` traces its `.wasm`, and `next.config.ts` names it in `turbopackAdditionalRoots`. The engine's Rust source under `engine/` and `engine-wasm/src/` is not read: the module is committed, and `make lint` fails while it differs from what its source generates.
  - `.gitignore` at the root: Tailwind's source detection skips the files git ignores, so the root file can change which files under `web/` it scans for classes.

  The first three are what `web/Dockerfile.dockerignore` admits. `web/src/__tests__/vercel-config.test.ts` fails when a link under `web/` or an entry of `turbopackAdditionalRoots` points outside `web/` anywhere but the first three.
- `VERCEL_GIT_PREVIOUS_SHA` is the commit of the branch's last successful deployment, set only where an Ignored Build Step is (Vercel's [system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables), updated 2026-07-15), so a push of several commits is compared with what was deployed, not with `HEAD^`. A cancelled build is not a successful one, so the changes it skipped count at the next push. A branch's first deployment has no previous commit, and `git diff` fails on the empty one, so it builds; so does a previous commit outside Vercel's clone, which holds the last 10 commits.
- A skipped build still counts: Vercel cancels it, and its project settings page states that a build cancelled by the Ignored Build Step counts toward the deployment quotas, Hobby's 100 a day among them, and the concurrent build slots. A cancelled deployment is kept for 30 days on Hobby ([deployment retention](https://vercel.com/docs/deployment-retention), updated 2026-09-16).
- A change made only in Vercel's settings, such as an environment variable, reaches no commit, so it is deployed by a redeploy from the dashboard with "Use project's Ignore Build Step" unchecked.

### Image

- `web/Dockerfile` is built from the repository root: `docker build -f web/Dockerfile .`, with both variables as `--build-arg`. `web/Dockerfile.dockerignore` admits only `web/`, `app/assets/fonts/` and `engine-wasm/pkg/` ([ADR 0022](adr/0022-study-on-the-web-with-the-engine-in-the-browser.md)).
- Three stages install the locked packages, build, and copy the standalone server, the static files and `public/` into the runtime stage. Each starts from the same index digest of `node:24.22.0-trixie-slim`, and the frontend is pinned by digest in the `# syntax=` line.
- The runtime stage runs `node server.js` on port 3000 as the base image's `node` user, uid 1000.
- Dependabot's `docker` entry for `/web` proposes only a new digest of the same `node:24.22.0-trixie-slim` tag; it ignores every Node.js release change. `make lint` fails while a `FROM` names another release than `web/.nvmrc`, and `scripts/web.ts` fails while the running Node.js differs from that file, so a release change moves `web/.nvmrc`, the `node-version` of `.github/workflows/ci.yml`'s `setup-node` step and the three `FROM` digests together, which Dependabot cannot do. The PM moves them, in one PR, to a new LTS release verified per ci.md.
- What the image runs is the web app alone; nothing in it may reach a Supabase secret.

### Session and proxy

Sign-in and the account page are the `account` feature's ([`web-account.md`](web-account.md)); this section states the session every route reads.

- The session is Supabase Auth's, in the cookies `@supabase/ssr` writes. `web/src/supabase/` holds the server client, over the request's cookies, the browser client, and `readSession`, which verifies a session with `getClaims` and returns `signed-in` with the email, `signed-out`, or `unreachable`.
- The server client waits for the request (`connection()`) before it starts: Supabase Auth's client reads the clock as it starts, which a prerender, a link's prefetch included, refuses.
- `web/src/proxy.ts` runs on every path but `/api`, `_next/static`, `_next/image`, `favicon.ico`, `brand/`, `google/` and the `.svg`, `.png` and `.webmanifest` files at the root of `public/`. A deeper path runs it whatever its extension, so `/admin/x.png` moves like any admin path and the admin host's `/decks/a.svg` is looked for in the area. It serves the two hosts `KNOWNO_SERVICE_ORIGIN` names ([ADR 0178](adr/0178-serve-the-admin-area-at-admin-knowno-app-from-the-same-web-app-routed-by-host-in-its-own-shell-and-session.md)), as Next.js 16.4.1's multi-tenant guide recommends one app serving several:
  - **Which host** a request is for, the proxy reads from its headers, since behind `next start` and the standalone server the request's URL names the server's own address. It accepts only the two hosts the variable names, port included. The Host header decides where it names one of them. Otherwise `X-Forwarded-Host` decides where it names one: a Server Action's redirect is rendered by a fetch to the server's own address that carries the action's forwarded host and not its Host. Where the two headers name different hosts of the two, as a client does to reach the area on the service's host, the proxy answers 421 and reads no session; under `next dev`, whose own address is the service's, the action's fetch is refused the same way and Next.js leaves that redirect to the browser. A host neither names, an IP address or a preview's `*.vercel.app`, is served as the service.
  - **The admin host**, `admin.knowno.app`, and `admin.localhost:<port>` on a machine and in the e2e specs, which the browser sends to the loopback with no DNS and `next dev` admits. There the proxy rewrites every path into the admin area's routes under `web/src/app/admin/`, `/users` serving `/admin/users`, but `/auth/callback`, and hands the page the configured service origin in the request header `x-knowno-service-origin`; a page of the service is looked for in the area and not found. A `signed-out` visitor goes to that host's `/login` from every path but `/login` and `/auth/callback` ([`web-admin.md`](web-admin.md)).
  - **On every other host**, `/admin` and every path below it move, before the session is read, by a permanent redirect (308) to the same path on the configured admin origin, never one built from a header, the query kept: `knowno.app/admin/users?q=kim` to `admin.knowno.app/users?q=kim`.
  - On both, a `x-knowno-service-origin` the client sent never reaches a page: the proxy removes it, and on the admin host sets its own.
  - On both it refreshes the session cookies, which `@supabase/ssr` writes host-only, so each host holds a session of its own. On the service's host it sends a `signed-out` visitor to `/login` from every path but `/login`, `/auth/callback`, `/terms` and `/privacy`. An `unreachable` Supabase lets the request through, so an outage signs no one out. A signed-out visitor sent from `/oauth/consent` leaves the consent's id in the cookie `smartman-oauth-consent` for ten minutes, and a signed-in visit to `/`, where sign-in lands, opens that consent again and deletes the cookie; an id not of Supabase Auth's form is never kept or followed ([`mcp.md`](mcp.md) §Consent page, [ADR 0126](adr/0126-connect-claude-and-chatgpt-through-one-remote-mcp-server-acting-as-the-signed-in-user.md)).

### Server reads

- The web app is online-first: it reads and writes the server tables of [`server.md`](server.md) with the user's session, under row-level security, and keeps no local database. The `decks` feature creates decks and cards, edits a stored card and transports bounded photo uploads through authenticated Server Actions, and photo import's save merges a duplicate's back into the card it repeats ([`web-decks.md`](web-decks.md)).
- Reads run on the server, in each page's Server Component, and read only what the page shows, with no cache ([ADR 0030](adr/0030-read-only-what-each-web-page-shows-and-size-the-web-from-the-app-tokens.md)). Each feature's document lists what its pages read.
- Each read keeps the signed-in user's own rows, since row-level security also lets every user read other users' public decks and their cards ([`server.md`](server.md)), leaves out every deck and card with `deleted_at` set and every card of such a deck, and parses each row at the boundary. It reads its tables in pages of 1000 rows, PostgREST's `max_rows` in `supabase/config.toml`: the first page with PostgREST's exact count, then every remaining page together, so it waits on two requests at most. A failure reaches the page as a value, `unreachable`, `rejected`, `failed` or `unreadable`, which it shows as one sentence in place of the list, under the page's heading, with its next step: "로그인" for `rejected`, and otherwise "다시 시도" (`web/src/design/read-failure.tsx`'s `ReadFailureMessage`, the one alert every read failure, the admin area's, 설정's and the AI consent page's included, draws with only its own sentences), which reads the page again through the router's `refresh()`, once per press (#276); the codes map as the phone's do ([`sync.md`](sync.md)). 노트 keeps "내 노트" as its heading, and a deck's page the way back to 노트 under "노트를 불러오지 못했어요".

Arguments given to it (`scripts/run.sh test-web e2e/home.spec.ts -g "fits 홈" --repeat-each 50`) go to `playwright test` as given, which then selects what runs, so no spec has to run a test; the count names them beside the selection (#614). Without Docker or `node` it prints the skip and why, or fails where `CI` is set.
- A known trade-off: listening on 0.0.0.0, the server `scripts/test-web.ts` starts answers the local network on its port from 54600–54699 for the length of a run, with an app built against the throwaway stack and its test accounts. 127.0.0.1 would keep it to the machine, and loops the admin host's rewrite (above).
- A step in either spec that clicks or presses a key on a page just loaded goes through `untilReacted` (`web/e2e/until-reacted.ts`): it acts only while the page shows no reaction and ends once it does, since an action before the page hydrates finds no handler and the server-rendered markup is there before then (#152).
