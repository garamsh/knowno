# Web admin

The web's `admin` feature: the admin area at `admin.knowno.app`, its host, sign-in, shell, gate, sections, actions and reads. The role, the audit log and the functions behind it are [`server.md`](server.md)'s.

## Current decisions

### Area

- Operators run the service from its own host, `admin.knowno.app`, on the web only; the app has no admin screen ([ADR 0070](adr/0070-run-the-service-from-a-web-admin-area-whose-role-and-audit-log-live-in-the-database-and-whose-every-read-and-write-is-checked-there.md), [ADR 0178](adr/0178-serve-the-admin-area-at-admin-knowno-app-from-the-same-web-app-routed-by-host-in-its-own-shell-and-session.md)). The same web app serves it: the proxy rewrites each path of the admin host into `web/src/app/admin/` and moves the service's `/admin/*` there ([`web.md`](web.md) §Session and proxy), so every address in this document is a path on the admin host, `/users` being `admin.knowno.app/users`, served by the route `/admin/users`. The area's links, redirects and history entries name these paths; its Server Actions' `revalidatePath("/admin", "layout")` names the route, as Next.js asks behind a rewrite.
- **Sign-in.** The admin host signs in on its own, since the session's cookies stay on the host that set them: a signed-out visitor goes to its `/login` (`web/src/app/admin/login/page.tsx`), "관리자 로그인" under the brand over "관리", with the sentence "관리자 계정으로 로그인해 주세요. 서비스의 로그인과는 따로예요.", Google's and Apple's buttons and the reason a sign-in failed, as the service's `/login` draws them ([`web-account.md`](web-account.md)), and no link into the service. The code exchange is the service's `/auth/callback`, on the admin host, which opens its `/`.
- **The gate.** The area's layout, `web/src/app/admin/(area)/layout.tsx`, renders nothing until the server's `is_admin` answers, inside a Suspense boundary with an empty fallback: an admin then sees the shell and the page; a signed-in account that is not an admin gets one line, "관리자만 들어올 수 있어요.", under the brand, with "다른 계정으로 로그인", which signs it out of the admin host and opens its sign-in, and nothing of the area; a server that cannot answer gets the error page. The area's pages set no metadata but the sign-in's, "관리자 로그인 · 알아몰라".
- **The shell** (`admin-shell.tsx`) has none of the service's menus. From 1024 px a side menu 240 px wide on the surface, pinned as the page scrolls, holds the brand, the lockup over "관리", which opens 처리할 일, the section menu, and at its foot, above a hairline, the admin's email, "서비스 열기" beside Lucide's external-link icon, hidden from assistive technology (the arrow character is in neither Jua nor Pretendard ExtraBold), which opens the service's address, handed to the page by the proxy, in a new tab, and 로그아웃, which signs this host out alone and opens its sign-in. Below 1024 px a bar over the page holds the brand and "메뉴", which opens the same menu and foot as a full screen, "관리 메뉴" beside "닫기", through `useModalDialog`; a section's link there drops the screen's history entry, closes it and opens the section, and Escape and the browser's back close it. The page sits in one `main` up to 1040 px wide, reached by "본문으로 건너뛰기".
- The role and every check live in the database ([`server.md`](server.md) §Admin area): every read and write is one of the server's admin functions, called with the user's session and the publishable key, and each refuses a caller who is not an admin. The web holds no service-role key and no admin's email or id.
