# Web study

The web's `study` feature: 홈's hero, the study page and its session, the 기록 page, the study day and its time zone, the queue and today's list, the engine in the browser and on the server, and the answers' writes. The pages' shell and the server reads they share are [`web.md`](web.md)'s; the app's `study` domain is [`study.md`](study.md).

## Current decisions

### Reads

- `/` (홈) reads `decks`' `readDeckList` (every deck, and each card's id, deck and creation time, without its sides) and `study`'s `readToday` with the streak and the week, the last seven study days' distinct cards that one more `study_record_days` request in the same batch gives, counted by `studyDayCounts` as `/record` counts them, together with the session's email for the profile button ([ADR 0165](adr/0165-open-on-today-over-the-last-seven-days-move-the-notes-to-a-tab-and-open-settings-from-the-profile-button.md)).
- `/record` (기록) reads `study`'s `readRecord`: the server's `study_record_days` and `study_record_cards` in two requests sent together, each row parsed at the boundary, in the day of the cookie's zone, and the cards' answers folded through the engine on the server, where a state or an answer the engine refuses reads as `unreadable` ([`server.md`](server.md), [ADR 0047](adr/0047-read-the-web-record-through-two-server-functions-and-fold-it-through-the-engine-on-the-server.md)).
- `/study` reads `readLibrary` over the decks it names (those decks and their cards with both sides) and `readToday` with the streak, together. `readLibrary` gives each card's photos and sounds the URL it signed for the user, each at `{user}/{media id}` for 4 hours, through `decks`' media path ([`web-decks.md`](web-decks.md) §Media), and the page draws and plays them from it, signing nothing of its own; a file Storage signs none for, and every file when the request fails, has no address ([ADR 0112](adr/0112-store-an-audio-block-by-media-id-and-length-up-to-60-seconds-and-play-the-front-s-sound-once-as-a-study-card-appears.md), [ADR 0163](adr/0163-store-a-web-card-s-new-photos-and-sounds-one-request-each-at-save-and-release-what-a-refused-or-edited-card-lets-go.md)).
- `readToday` reads today's study day ([ADR 0033](adr/0033-count-cards-left-per-study-day-from-04-00-and-continue-as-unrecorded-practice.md), [ADR 0043](adr/0043-set-each-day-s-new-cards-from-the-user-s-recency-weighted-study-time-and-pace-and-count-an-answer-s-time-only-in-the-foreground.md)): every answer since the day began, then, for the cards answered today, their answers before it, in requests of 100 card ids each, sent together, to count the new cards first answered today and the reviews the day held when it started; the stored state of every reviewed card, across every deck (`readCardStates`); and the server's `study_days_before` over the latest 30 study days before today in one request, each answer counted up to 30 s, from which `web/src/features/study/study-time.ts` computes the user's pace as the phone does; the user's own `study_settings` row, the daily study minutes, or 20 without one ([ADR 0085](adr/0085-fill-each-day-s-new-cards-from-the-daily-study-minutes-the-user-sets-stored-per-user-on-the-server-and-synced.md)); from the minutes, the reviews due as the day stood when it started and the pace, `study-time.ts` computes the day's new cards, and `readToday` returns the minutes and those reviews beside the day; and, for the streak, the server's `study_streak_before` over the days before today in one request, in one request ([`server.md`](server.md)). It reads the day in the time zone the cookie `smartman-tz` names, which the root layout's head script writes on every page from the browser's `Intl` zone, the sign-in page included, so it is set before any page that counts; without the cookie, or with a zone the server does not know, it reads the day in Asia/Seoul (`web/src/features/study/time-zone.ts`).

### Queue and today's list

- `web/src/features/study/queue.ts` holds the queue rules of [`study.md`](study.md), in one module: the study day from 04:00 to 04:00 in a time zone, with its new cards less those first answered in it across every deck, never below zero and not carried over, and the constants of a day's new cards, which `study-time.ts` applies; a card due when it falls due before the day ends; a backlog above three days of reviews due, its due cards earliest due first in shuffled runs of ten and no new card; otherwise the due cards and as many new ones as the day has left, oldest first, shuffled; a "모른다" shown again after 3 to 5 other cards; the streak; and the counts the deck screens show, from the same selection ([ADR 0025](adr/0025-order-a-review-backlog-by-due-date-and-pause-new-cards.md), [ADR 0033](adr/0033-count-cards-left-per-study-day-from-04-00-and-continue-as-unrecorded-practice.md)). The study page selects the queue on the server, in the day `readToday` read, and the browser orders it from a random source seeded with that time, so the server's render and the browser's agree. It also gives each card each side's one line of text, which `decks` describes, since the study screen is a client module and cannot import `decks`' entry point ([`structure.md`](structure.md)). Every random choice of a session, its order, each re-show gap and each answer's fuzz factor, comes from that one source.
- `web/src/features/study/today-list.ts` places cards in today's list through the WebAssembly's `todaysList` ([ADR 0061](adr/0061-keep-a-card-failed-today-in-today-s-list-until-it-is-passed-through-a-pure-engine-function-over-the-day-s-reviews.md)), and throws where the list does not place every card given. `dayPlanOf` makes the day plan from it, as the phone's does: the selection the rules take, the cards still on "모른다" that they did not, and the cards done ([ADR 0062](adr/0062-take-the-study-queue-and-the-top-bar-s-count-from-today-s-list-so-a-reopened-day-goes-on-in-the-app-and-the-web.md)).
  - 홈's count and its notes' chips, and the note page's count, all count the plan's left cards, `countDay`, so they agree with the study page and the phone. Each page loads the server's engine module first (`readyServerEngine`) and shows its own failure message if it cannot.
  - The study page's server sends the selection, the cards still on "모른다" apart from it, whether a card of the day is done, the day's bounds, today's answers with their cards and times, and the states of the cards answered today. The browser's session puts each card still on "모른다" back after a re-show's gap or at the end, counts its own answers in the day it opened in, after 04:00 too, and counts the day as the phone's does.
  - The screen starts the session once the engine's module has loaded in the browser, showing the page's skeleton until then. If the module fails to load, it says "학습 화면을 불러오지 못했어요. 연결을 확인하고 다시 시도해 주세요." with "다시 시도", which loads it again, and "그만하기", a link to where the session was opened from.
  - When the decks cannot be read, the page says why, as the other pages do, with "그만하기", a link to where the session was opened from: the study page stands outside the shell, so no menu leads back.
- The day plan (`dayPlanOf`, `today-list.ts`) leaves out the cards studied past it, `studyDay`'s `extra`, as the phone's does: neither selected, left nor done ([ADR 0087](adr/0087-count-the-cards-studied-past-the-day-s-plan-apart-so-they-never-reopen-the-day-or-grow-its-goal.md)).
- `web/src/features/study/overview.ts` copies `overview.dart`'s definitions: progress at 21 days, a deck's counts and the next review, with `chartDays` and `masteredInterval` equal to `overview.dart`'s.
- Each queue constant in `queue.ts` equals `app/lib/study/src/queue.dart`'s of the same name, and `studyDayStartHour` equals the hour `public.study_day_start_hour()` returns in the latest migration defining it ([`server.md`](server.md)).
- `web/src/features/study/stats.ts` and `study-time.ts` give the figures of the phone's `app/test/study/stats_test.dart` and `study_time_test.dart` on the same fixed histories, but for the mastered gain, which the web counts from four weeks back and the phone, since [ADR 0120](adr/0120-state-today-s-progress-once-put-every-study-button-in-its-card-name-the-record-plainly-and-draw-photo-import-s-bar-checks-and-moves-as-the-other-screens-do.md), from the chart's first week, until a web follow-up.

### Engine and writes

- The engine runs in the browser ([ADR 0022](adr/0022-study-on-the-web-with-the-engine-in-the-browser.md)). `web/src/features/study/engine-wasm` links to `engine-wasm/pkg/`, which `next.config.ts` admits in `turbopackAdditionalRoots`; the generated glue fetches its `.wasm`, which the build serves as a static file. The screen starts fetching it when it opens. The `/record` page also runs it on the server: `web/src/features/study/engine-server.ts` reads the same module's file from the project's root, through that link, and instantiates it once per server process, for each card's recall and the states its answers fold into ([ADR 0047](adr/0047-read-the-web-record-through-two-server-functions-and-fold-it-through-the-engine-on-the-server.md)).
- Writes never hold the screen: an answer or a toggle changes it at once, and its write joins a queue that sends one write at a time, in order. A write replays the card's answers of this session, with their fuzz factors, from its state when the session opened, as the phone does, and the Server Action `recordAnswer` stores the result with the session it verifies ([`sync.md`](sync.md)). `recordAnswer` returns the server's time once both rows are stored. The browser keeps the latest such time in a module-level store that outlives the screen (`web/src/features/study/answer-saved.ts`). 홈, the 노트 page and 기록 each wrap their content, inside its Suspense boundary, in `study`'s `StudyStateRead`. That Server Component calls `connection()`, takes the server's time before the content renders and reads, and hands it to `StudyFreshness`, which draws nothing. `StudyFreshness` calls `router.refresh()` once when an answer stored after that time has landed: when it mounts, as when the router draws the page again from its cache; when it shows again after a back; and while shown, when one still in flight lands. `recordAnswer` revalidates nothing ([ADR 0169](adr/0169-read-the-pages-that-show-study-state-again-in-the-browser-once-an-answer-saved-after-they-were-read-lands.md), #603). Each new review's id is a version 7 uuid from the `uuid` package's `v7()` ([ADR 0034](adr/0034-key-synced-rows-by-client-made-uuids-purge-tombstones-past-a-revision-horizon-and-index-each-query.md) §1).

The screen says what failed in one sentence with "다시 시도", which sends them again; the answers stay in the stack.
